# V1.90 — Universal Visual Context Audit — Part 05

## AUD-V190-026 — Appearance is already a separate architecture

The permanent vision explicitly separates appearance from structure/geometry and defines an appearance-resolution pipeline. Evidence: `ENGINE_VISION__part_04.md:3-43`.

A generic `AppearanceDomain` enum exists with BASE, MATERIAL, STATE, EFFECT, LIGHTING, COLOR, TRANSMISSION, REFLECTION and EMISSION.

Evidence: `src/visual_engine/runtime/appearance_contract.py:22-38`.

## AUD-V190-027 — Domain contracts vs domain algorithms

The current appearance contract validates closed vocabularies for BASE, MATERIAL, COLOR, LIGHTING, TRANSMISSION, REFLECTION and EMISSION.

Evidence: `appearance_contract.py:64-130`.

But contract existence is not equivalent to a complete resolver implementation. The audit found concrete authoritative resolvers for BASE, MATERIAL and COLOR. The other domains currently have validated contracts/inputs but no equivalent general physical/visual domain algorithm established as the generic production renderer's shading engine.

**Classification:** appearance contract = `VERIFIED`; complete appearance intelligence engine = `PLANNED/PARTIAL`.

## AUD-V190-028 — COLOR was not simply forgotten

COLOR has a real canonical layer: color spaces, typed COLOR input/resolution, BaseColor and Palette infrastructure, persistence and provenance. V1.36 explicitly closed the downstream audit without inventing a new generic transformation; V1.37-1.40 continued effect-color/cache closure without adding speculative color algorithms.

Evidence: `CURRENT_STATUS__part_02.md:1-100`; `ENGINE_VISION__part_08.md:90-117`.

**Classification:** canonical COLOR foundation = `VERIFIED`; complete Color/Appearance Intelligence Engine = `PLANNED/PARTIAL`.

## AUD-V190-029 — COLOR vs APPEARANCE distinction

The audit confirms that COLOR and APPEARANCE must not be treated as synonyms.

COLOR answers representation/authority/transformation questions around color data. APPEARANCE composes domain contributions such as base, material, lighting, transmission, reflection and emission. The generic appearance contract explicitly keeps these domains separate.

This is a **formal clarification**, not a claim that the project must immediately create a second COLOR engine.

## AUD-V190-030 — Material

`MaterialContract` is a real renderer-neutral value contract and `material_resolution.py` provides an authoritative-record resolver. It does not yet simulate physical shading.

Evidence: `components/common/visual_contract.py:70-93`; `runtime/material_resolution.py:41-115`.

**Classification:** MATERIAL contract/resolver = `VERIFIED`; full physical material response = `PLANNED`.

## AUD-V190-031 — Lighting / transmission / reflection / emission

The generic appearance contract declares validated fields for these domains, but the audit does not promote them to a complete lighting/optics engine merely because their schemas exist.

**Classification:** contracts = `VERIFIED`; complete domain algorithms = `PARTIAL/PLANNED`.
