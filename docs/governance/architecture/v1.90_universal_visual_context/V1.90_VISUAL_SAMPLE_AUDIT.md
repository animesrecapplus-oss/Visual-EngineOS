## EVD-V190-002 — Bilateral defect sample

The production path creates `left_eye` and `right_eye` at symmetric anchors but `_eye_component_inputs()` does not supply side identity. Direct geometry inspection reproduced the left-eye terminal inversion described in the audit:

`left_eye / single`: inner `(-0.39,0)`, outer `(-0.17,0)`.

`left_eye / image_left`: inner `(-0.17,0)`, outer `(-0.39,0)`.

The canonical `build_eye_pair()` sample instead uses `image_left` and `image_right` and reports the expected inward medial terminals.

Artifact: `V1.90_EYEPAIR_CANONICAL.svg/.png`.

## EVD-V190-003 — Iris/render-order sample

The generic production geometry adapter emits iris/pupil as primitives while aperture/lid geometry is represented as paths. The generic SVG renderer emits all path elements before all primitive elements and has no generic mask/clip application for these primitives.

The specialized ocular SVG renderer separately creates an aperture `clipPath` for internal ocular content. This proves the architectural difference without claiming that the default frontal image alone visibly demonstrates an iris overflow defect.

## EVD-V190-004 — Boundary sample

A left-eye opening reduction was rendered at `opening=0.3`. The iris shrinks with the eye geometry and remains visually small in this particular sample; this does **not** prove generic clipping is correct. It proves only that this boundary input does not expose a visible overflow in that specific parameter state.

Artifacts: `V1.90_BOUNDARY_LEFT_EYE_OPENING_0.3.svg/.png`.

## EVD-V190-005 — Negative visual claim

No claim is made that the current renderer is final-quality, physically correct, or artistically complete. The sample exists to verify architectural behaviour and expose the difference between isolated ocular rendering and the production HumanFace path.
