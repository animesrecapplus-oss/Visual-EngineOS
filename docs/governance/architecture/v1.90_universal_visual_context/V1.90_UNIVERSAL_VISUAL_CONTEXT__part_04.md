# V1.90 — Universal Visual Context Audit — Part 04

## AUD-V190-020 — Bilateral eye semantics: canonical pair path

The canonical `build_eye_pair()` path already supplies `side="image_left"` to the left eye and `side="image_right"` to the right eye.

Evidence: `src/visual_engine/components/face/eyes/pair.py:145-188`.

The pair policy also enforces human-default morphology symmetry and bounded asymmetry.

**Classification:** isolated/canonical eye-pair bilateral semantics = `VERIFIED`.

## AUD-V190-021 — Bilateral eye semantics: HumanFace production path

The production HumanFace adapter `_eye_component_inputs()` constructs `EyeGeometryInputs(parameters=..., center=...)` and does **not** propagate the eye side. `EyeGeometryInputs.side` therefore remains its default `"single"`.

Evidence: `src/visual_engine/components/face/generators.py:107-116`; `src/visual_engine/components/face/eyes/generator.py:26-36`.

The HumanFace composite then merges the two already-generated child geometries; it does not repair their lost bilateral identity.

Evidence: `generators.py:184-216`.

**Classification:** real production defect = `VERIFIED`.

## AUD-V190-022 — Defect reproduction

For the V1.89 production defaults, direct geometry inspection gives:

- `left_eye` with `side="single"`: inner canthus `(-0.39,0)`, outer canthus `(-0.17,0)`;
- `left_eye` with `side="image_left"`: inner `(-0.17,0)`, outer `(-0.39,0)`;
- `right_eye` is unchanged between `single` and `image_right` in this symmetric default.

The canonical pair therefore has the expected inward medial terminals, while the HumanFace production path loses the left-side semantic frame.

**Classification:** confirmed with executable sample; this is not a Gaze solver defect.

## AUD-V190-023 — Specialized vs generic eye rendering

The specialized ocular SVG renderer creates an aperture `clipPath` and renders internal ocular elements through that clip. Evidence: `src/visual_engine/render/svg.py` (`render_eye_svg`/`render_eye_pair_svg` path and clip construction).

The generic production `render_geometry_svg()` rejects unresolved masks, orders paths deterministically, then emits all supported primitives after all path elements. Evidence: `src/visual_engine/render/geometry_svg.py:153-220`.

The eye geometry adapter represents iris/pupil as renderer-neutral primitives and the aperture/lids as paths. Evidence: `src/visual_engine/components/face/eyes/generator.py:80-145`.

**Classification:** specialized ocular clipping = `VERIFIED`; generic production primitive clipping against the aperture = `ABSENT/NOT_IMPLEMENTED`.

## AUD-V190-024 — Iris depth/occlusion conclusion

The audit therefore confirms a real architectural mismatch: the specialized ocular renderer has an aperture clip, while the generic production renderer has no equivalent generic mask/clip application for iris/pupil primitives.

The default front render may not visibly expose the defect because the default iris is generated within the visible aperture. A boundary/interaction condition can nevertheless expose the missing generic clipping semantics.

**Classification:** missing generic iris/lid occlusion contract = `VERIFIED GAP`; root owner is **not yet promoted**.

## AUD-V190-025 — Correct ownership rule

Do not patch Gaze for either defect. Gaze controls ocular internal assembly; the left/right loss occurs at the HumanFace→Eye input boundary, while the clipping gap occurs at the geometry/render-plan/mask boundary.

Any runtime change must first perform a fresh owner/consumer/impact audit.
