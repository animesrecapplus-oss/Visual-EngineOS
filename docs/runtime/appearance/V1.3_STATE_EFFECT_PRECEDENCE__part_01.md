# V1.3 — State / Effect Precedence Contract

## Why this step exists

A visual component is not resolved by simply collecting every state and every effect. In a real entity graph, mutually incompatible states can arrive from different hierarchy levels, while several external effects can target the same atomic component.

Examples:

- `open` versus `closed` eyelid state;
- `normal` versus `damaged`;
- `dry` versus `wet`;
- a local state versus an explicit shot/context state;
- two shadows from different occluders;
- occlusion plus opacity;
- several color/tint effects.

Without an explicit contract, the renderer eventually becomes the accidental conflict solver. That is forbidden.

## State model

`StateLayer` now carries:

- `name` — logical state name;
- `enabled` — whether the state is a candidate;
- `priority` — precedence weight;
- `group` — optional exclusive group;
- `conflicts` — explicit incompatible state names;
- `requires` — state names that must remain active;
- `values` — semantic payload, not yet an implicit visual override.

### Precedence

Candidates are ranked by:

1. `priority`;
2. source rank (`ResolutionContext` is explicit external intent);
3. hierarchy specificity (target is more specific than ancestors);
4. stable state/source identifiers.

The default context priority is `1000`. A component may deliberately exceed it with a higher priority; this makes the boundary explicit instead of hardcoding context as absolutely dominant.

### Same logical state from multiple ancestors

A state name represents one logical activation. If multiple ancestors contribute the same state, only the highest-precedence activation survives. The lower candidate is recorded as rejected in provenance.

### Exclusive groups

Only one accepted state can occupy a given group. The winner is the highest-precedence candidate.

Example:

```text
lid group:
    open      priority 10
    closed    priority 20

=> closed
```

### Explicit conflicts

A state may declare incompatible states through `conflicts`. The resolver treats a conflict symmetrically: either declaration is sufficient to reject the lower-precedence candidate.

### Requirements

A state with `requires=(...)` is removed if any requirement is absent. Requirement elimination is repeated to a fixed point, because removing one state can invalidate another dependent state.

Self-conflicts and self-requirements are rejected at the model boundary.

## State provenance

Resolution provenance records both acceptance and rejection:

```text
state=closed ... accept ... passed group/conflict precedence
state=open   ... reject ... exclusive group 'lid' won by closed
```

This is deliberately stronger than storing only `active_states`; a large graph must be debuggable without reconstructing the resolver's decisions manually.

## Effects

`VisualEffect` is the generic external effect envelope. It is intentionally renderer-neutral.

Supported effect kinds in this checkpoint:

- `shadow`;
- `occlusion`;
- `tint`;
- `opacity`;
- `visibility`.

Each effect has:

- stable ID;
- kind;
- priority;
- alpha;
- color;
- opacity factor;
- visibility factor;
- source ID;
- optional target component;
- deterministic metadata.

Duplicate effect IDs in one context are rejected because they would make cache identity and provenance ambiguous.

## Composition laws

Effects do not silently replace one another.

### Shadow / tint

Color effects are applied in deterministic priority order.

### Opacity

Multiplicative:

```text
opacity_final = opacity_base × Π(effect.opacity_factor)
```

### Visibility

Multiplicative:

```text
visibility_final = visibility_base × Π(effect.visibility_factor)
```

### Occlusion

The current generic layer accepts a scalar coverage alpha:

```text
visibility *= (1 - alpha) × visibility_factor
opacity    *= opacity_factor
```

This is intentionally **not** a geometric occlusion solver. Fingers, glasses, hair, eye patches and arbitrary objects will later compute this alpha from geometry and feed the same contract.
