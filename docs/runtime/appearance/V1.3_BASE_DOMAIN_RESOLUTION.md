# V1.3 — BASE Domain Resolution

## Objective

Implement the first real appearance-domain algorithm after the generic resolver
input/result contract, without introducing implicit composition, material, lighting
or color-intelligence behavior.

## Semantic decision

The current `BASE` contract defines one required field: `base_color`. It does not
define a precedence relation between multiple BASE contributions, nor does the
resolver input contain an explicit underlay/background for alpha compositing.

Therefore this first algorithm uses a deliberately strict **single authoritative
BASE contribution** rule:

- zero BASE contributions → `REJECTED`;
- exactly one opaque contribution → `RESOLVED`;
- more than one contribution → `REJECTED` because precedence/composition is undefined;
- contribution opacity different from `1.0` → `REJECTED` because no underlay is defined;
- `#RRGGBBAA` is accepted by the existing contract and preserved as data; its alpha
  is not composited or interpreted here;
- output is lower-case hexadecimal representation only; no color-space conversion,
  gamut mapping, perceptual adjustment or shading is performed.

This is intentionally narrower than a future appearance compositor. The engine must
not manufacture a visual rule merely because several values happen to be present.

## Input/output path

```text
AppearanceContribution(BASE)
        ↓
Domain Contract Validation
        ↓
DomainResolutionInput
        ↓
resolve_base_domain()
        ↓
DomainResolutionResult(BASE)
        ↓
existing result validator
```

The generic result validator remains authoritative for output vocabulary, provenance,
input identity and dependency identity.

## Invalidation and provenance

The BASE result retains the exact `input_digest`, resolver identity/version,
contribution identity and dependency identity. Changes to active states or upstream
dependency digests therefore change the resolution identity conservatively, even when
the BASE algorithm does not currently interpret those state values.

This avoids stale-cache ambiguity. A later optimization may narrow dependency scope
only after the dependency semantics are explicit and tested.

## Explicit nonclaims

This checkpoint does **not** implement:

- multiple-base layering or alpha compositing;
- color mixing or color-space conversion;
- material response;
- lighting/shadows;
- transmission/refraction;
- reflection;
- emission;
- state mutation;
- geometry mutation;
- renderer-specific behavior;
- visual quality scoring.

Those remain separate domain/engine responsibilities.

## Verification

The BASE resolver has dedicated tests for authority cardinality, opacity semantics,
RGBA preservation, resolver identity, provenance, dependency invalidation, state
identity invalidation, malformed payload rejection and wrong-domain routing.
