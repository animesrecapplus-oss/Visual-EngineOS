# V1.3 — Appearance Layer Resolution

## Purpose

This checkpoint defines how the existing `Component.appearance` list enters the
renderer-neutral `AppearanceResolutionInput` contract.

It does **not** invent an appearance inheritance model. Only the target
component's own `appearance` list is considered.

```text
Component.appearance
        ↓
explicit layer binding
        ↓
AppearanceLayerResolution
        ↓
AppearanceContribution
        ↓
AppearanceResolutionInput
```

## Layer domain is explicit

`AppearanceLayer` itself contains only `name`, semantic `values` and `opacity`.
It does not declare whether its payload is color, material, lighting, reflection,
etc. Therefore an `AppearanceLayerBinding` is required to assign its domain.
An unbound layer is reported as unresolved and is never guessed into `BASE` or
`COLOR`.

## Local versus inherited

The resolver consumes only `component.appearance`.

No ancestor appearance is traversed. Existing visual inheritance rules for
`VisualContract` / `VisualOverrides` are not reused for appearance layers because
that would silently create a new inheritance semantic for a different contract.

A future inherited appearance model must introduce an explicit source/binding
contract rather than being inferred here.

## Order and priority

Two distinct concepts are retained:

- **order**: contribution evaluation/order; explicit binding `order` wins, otherwise
the existing declaration index in `Component.appearance` is retained;
- **priority**: used only when an explicit conflict policy selects among members
of a conflict group.

Priority therefore never silently reorders ordinary appearance layers.

## Active states

A layer becomes state-dependent only through an explicit binding containing
`required_states` and an explicit `ALL_STATES` or `ANY_STATE` activation mode.
The resolver receives the already-resolved active-state set from upstream. It does
not resolve state conflicts itself.

## Effects

`VisualEffect` is already a typed contract. Target-applicable effects therefore
become `AppearanceDomain.EFFECT` contributions without interpreting their kind as
color, material or lighting semantics.

The existing effect policy remains responsible for effect composition.

## Conflicts and duplicates

- duplicate appearance layer names are rejected because the legacy model exposes
only `name` as layer identity;
- duplicate bindings are rejected;
- conflict groups require an explicit `AppearanceLayerPolicy`;
- `KEEP_ALL`, `HIGHEST_PRIORITY` and `REJECT_CONFLICT` are explicit;
- missing conflict policy fails closed;
- visual-effect IDs must remain unique.

No conflict is inferred merely because two layers share a target or domain.

## Provenance

Every accepted layer/effect contribution receives provenance containing source
component, layer/effect identity, domain, order, priority, active-state context
and a stable SHA-256 fingerprint.

## Invalidation / determinism

`AppearanceLayerResolution.dependency_digest` hashes the component appearance,
explicit bindings, policies, active states and target-applicable effects. The digest
is copied into `AppearanceResolutionInput.layer_resolution_digest`.

Bindings, policies and effects are canonicalized before hashing, so equivalent
caller input order does not change the digest. A local appearance change changes
the target's digest; unrelated components are not included.

This digest is a downstream appearance-layer dependency token. It does not replace
the existing graph `ResolutionFingerprint` and does not claim a global cache policy.

## Not claimed

This checkpoint does not implement:

- color mixing;
- palette generation;
- lighting;
- material shading;
- reflection/refraction;
- transmission solving;
- appearance inheritance;
- renderer output.
