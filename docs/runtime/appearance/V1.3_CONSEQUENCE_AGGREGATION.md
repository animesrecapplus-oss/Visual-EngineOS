# V1.3 — Consequence Request Aggregation, Conflict, Precedence & Idempotence

## Purpose

This checkpoint closes the boundary between declarative `ConsequenceRequest`
compilation and any future state/geometry/appearance mutation.

```text
AffectedRegionEvent / OccluderAttribution
        ↓
ConsequenceRule
        ↓
ConsequenceRequest
        ↓
Request Aggregation
        ↓
Conflict / Precedence Resolution
        ↓
ResolvedConsequence
        ↓
future downstream resolvers
```

The aggregation layer does **not** mutate state, geometry, appearance, effects,
or render output.

## Contracts

### 1. Exact idempotence

A request receives a stable SHA-256 semantic fingerprint. Repeating the exact
same request does not create another resolved request.

The fingerprint includes the rule, kind, target, semantic region, source event
key, explicit precedence, and payload. Causal provenance is therefore not lost
while deduplicating.

### 2. No implicit conflict

Two requests targeting the same component or region are **not** considered a
conflict merely because they share a target. A conflict group must be explicitly
declared through `payload["resolution_group"]` and a corresponding
`ConsequencePolicy`.

This prevents a generic request resolver from accidentally suppressing valid
independent effects.

### 3. Explicit aggregation modes

- `KEEP_ALL`: retain every distinct request in the group.
- `DEDUPLICATE`: retain distinct requests after exact fingerprint deduplication.
- `HIGHEST_PRIORITY`: retain the request with the greatest explicit
  `ConsequenceRequest.precedence`.
- `REJECT_CONFLICT`: reject all competing requests in a group rather than
  guessing a winner.

`ConsequenceRule.priority` remains rule-matching order. It is deliberately not
reused as downstream consequence precedence.

### 4. Provenance

Every accepted or rejected result retains:

- `rule_id`;
- `target_id`;
- `region_id`;
- complete `source_event_key`;
- request fingerprint;
- decision;
- competing fingerprints when a conflict/precedence decision occurs.

### 5. Determinism

Input order does not determine the result. Requests, policy groups, winners and
final digest are canonically ordered.

### 6. Fail closed

Duplicate policy groups and mixed target IDs are rejected. Unknown aggregation
modes cannot silently fall back to another behavior.

## Deliberate boundary

This checkpoint does **not** apply consequences. In particular, it does not
turn a visibility event into an eye state, deform geometry, recolor a component,
or create a visual effect. Those operations require their own downstream
resolvers and contracts.

## Known next audit

Before connecting mutation, the next gate must verify that downstream state/effect
precedence can consume `ResolvedConsequence` without duplicating the existing
state/effect policy engines. Appearance/color remains downstream of this gate.
