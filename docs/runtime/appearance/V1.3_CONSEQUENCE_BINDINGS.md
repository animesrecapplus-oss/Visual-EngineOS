# V1.3 — Consequence → State/Effect Binding Boundary

## Purpose

This checkpoint connects the already aggregated `ResolvedConsequence` objects to
the **existing** state and effect contracts. It is a compiler boundary, not a
second policy engine and not a mutation step.

```text
ConsequenceRequest
      ↓
Aggregation / Conflict / Precedence
      ↓
ResolvedConsequence
      ↓
Declarative Binding
   ┌──┴──────────┐
   ↓             ↓
StateActivation VisualEffect
   ↓             ↓
existing state  existing effect
policy          composition
```

## Explicit design rules

1. A consequence name is not automatically a state or effect. A binding must
   explicitly declare the mapping.
2. Missing bindings are returned as `unbound`; they are never guessed.
3. State precedence remains owned by `runtime/state_policy.py`.
4. Effect composition remains owned by `runtime/effects.py`.
5. Geometry and appearance consequences remain unbound until dedicated contracts
   exist.
6. The compiler does not mutate `Component`, `StateLayer`, geometry, appearance,
   or render output.
7. Provenance survives through stable request fingerprints and is embedded in
   generated effect metadata.

## State binding

`StateConsequenceBinding` maps a semantic consequence to a state name and may
explicitly provide group/conflict/requirement metadata. Request precedence is
converted into the activation priority using an explicit binding offset. The
state resolver then performs the actual precedence, exclusivity, conflict and
requirement resolution.

## Effect binding

`EffectConsequenceBinding` maps a semantic consequence to an existing
`VisualEffect` kind and its typed parameters. Effect IDs are derived from the
stable request fingerprint, so duplicate causal requests cannot silently create
ambiguous IDs.

## Fail-closed behavior

An accepted consequence with no binding is retained in `unbound`. This is
intentional: the engine must not infer that `"damage"` means a state, tint,
geometry deformation, or any other visual operation without an explicit contract.

## Verification

- full `pytest -q`: PASS;
- `python -m compileall -q src`: PASS;
- state precedence is resolved by the existing state policy;
- effect values are validated by the existing `VisualEffect` contract;
- geometry/appearance requests are not guessed into another domain.

## Boundary after this checkpoint

The engine can now compile validated consequences into the two existing downstream
envelopes without duplicating their policy engines. It still does not mutate the
entity graph.

The next logical gate is to define a **generic consequence application/resolution
transaction**: how accepted state activations and effects are attached to a
specific resolution context/component while preserving provenance, target/region
granularity, dependency fingerprints and deterministic invalidation. Appearance
and color remain downstream of that boundary.
