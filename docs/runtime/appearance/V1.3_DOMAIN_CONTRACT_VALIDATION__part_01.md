# V1.3 — Appearance Domain Contract Validation

## Purpose

This checkpoint closes the semantic gap between `AppearanceContribution` and the
future domain resolvers. A contribution may declare a domain, but that declaration
alone must not make arbitrary keys meaningful. This layer therefore defines the
closed vocabulary, value kinds and numeric boundaries of each rendering domain
before any algorithm is introduced.

```text
AppearanceContribution
        │
        ▼
Domain Contract Validation
        │
        ├── BASE
        ├── MATERIAL
        ├── COLOR
        ├── LIGHTING
        ├── TRANSMISSION
        ├── REFLECTION
        └── EMISSION
```

## Principle

**Validation is not interpretation.** The validator answers only: “Is this payload
legally shaped for the declared domain?” It does not blend colors, calculate
lighting, derive Fresnel response, convert units, shade materials, or render pixels.

The payload is also not normalized by the validator. The immutable
`AppearanceContribution` remains unchanged.

## Domain contracts

### BASE

Purpose: the intrinsic base appearance value before material/light interaction.

Allowed fields:

- `base_color`: hexadecimal `#RRGGBB` or `#RRGGBBAA`; **required**.

No material, lighting or optical parameters are accepted here.

### MATERIAL

Purpose: material identity and surface-response parameters that belong to the
material description itself.

Allowed fields:

- `name`: non-empty string.
- `roughness`: unit interval `[0,1]`.
- `metallic`: unit interval `[0,1]`.
- `transmission`: unit interval `[0,1]`.
- `emission`: unit interval `[0,1]`.

These fields are vocabulary-compatible with the existing `MaterialContract`; no
shading equation is introduced here.

### COLOR

Purpose: color-space-independent semantic color adjustments/pattern descriptors
that will later be consumed by the color resolver.

Allowed fields:

- `base_color`: hexadecimal color.
- `pattern`: non-empty string identifier.
- `palette`: tuple/list of non-empty string identifiers.
- `contrast`, `saturation`, `vibrance`, `lightness`, `temperature`: finite numeric
  values.

The numeric fields deliberately have no artificial `[0,1]` restriction at this
boundary because their eventual transfer functions have not yet been specified.

### LIGHTING

Purpose: declarative light-source/channel inputs, not illumination computation.

Allowed fields:

- `color`: hexadecimal color.
- `intensity`, `ambient_intensity`, `key_intensity`, `fill_intensity`,
  `rim_intensity`, `bounce_intensity`: finite non-negative numbers.
- `direction`: finite 2D or 3D vector.
- `temperature_kelvin`: strictly positive number.

Intensity is intentionally not capped at `1`; no renderer-specific exposure model
has been selected yet.

### TRANSMISSION

Purpose: declarative optical transmission parameters.

Allowed fields:

- `amount`: `[0,1]`.
- `ior`: finite number `>= 1`.
- `thickness`: finite number `>= 0`.
- `absorption_color`: hexadecimal color.
- `absorption_distance`: strictly positive finite number.

No refraction ray tracing, absorption equation or thickness interpretation is done.

### REFLECTION

Purpose: declarative reflective-response parameters.

Allowed fields:

- `strength`: `[0,1]`.
- `roughness`: `[0,1]`.
- `color`: hexadecimal color.
- `ior`: finite number `>= 1`.

No Fresnel computation, environment lookup or reflection sampling is performed.

### EMISSION

Purpose: declarative self-emission parameters.

Allowed fields:

- `color`: hexadecimal color.
- `intensity`: finite non-negative number.
- `temperature_kelvin`: strictly positive number.

No bloom, exposure, tone mapping or light propagation is performed.

## Closed-world rule

The seven rendering domains are **closed contracts**. An unknown key is a hard
validation error. This is intentional: a key such as `strength`, `color`, `pattern`
or `roughness` cannot acquire a different meaning merely because a caller placed it
inside another domain.

A future field must therefore be added to the domain contract explicitly, with its
value kind and boundaries documented and tested.
