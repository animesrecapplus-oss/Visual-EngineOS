# V1.3 — Consequence Resolution Bridge

## Purpose

This checkpoint closes the boundary between accepted consequence bindings and the existing component resolution contract.

```text
ResolvedConsequence
      ↓
ConsequenceBinding
      ↓
ConsequenceBindingResult
      ↓
ResolutionContext
      ↓
existing State Policy / Effect Policy
      ↓
ResolvedComponent
```

The bridge is deliberately not a second precedence engine.

## State path

`StateActivation` objects produced by consequence bindings are appended to the candidates collected by the existing `state_policy` resolver. The existing resolver remains the sole owner of:

- precedence;
- source rank;
- specificity;
- exclusive groups;
- symmetric conflicts;
- requirements;
- deterministic decisions.

## Effect path

`VisualEffect` objects produced by consequence bindings are appended to the immutable `ResolutionContext.effects`. The existing effect resolver remains the sole owner of:

- ordering;
- duplicate effect ID validation;
- shadow/tint composition;
- opacity composition;
- visibility composition;
- occlusion composition.

## Geometry and appearance

They remain explicitly unbound. The bridge does not guess that a geometry or appearance consequence is a state or effect.

## Cache / invalidation boundary

Consequence-derived state activations are part of `context_fingerprint`. Targeted effects continue to be filtered by the existing target-aware fingerprint logic. Therefore a consequence affecting one component does not automatically invalidate an unrelated sibling.

The resolution version is advanced to `8` because the semantics of the resolution context have changed.

## Fail-closed rules

- non-`ResolutionContext` inputs are rejected;
- duplicate effect IDs are rejected at the context boundary;
- effects targeting another component are rejected;
- unbound geometry/appearance requests remain unbound;
- no mutation of source components occurs.
