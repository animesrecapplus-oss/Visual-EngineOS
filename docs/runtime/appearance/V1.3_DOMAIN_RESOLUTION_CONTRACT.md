# V1.3 — Domain Resolution Contract

**Date:** 2026-09-15

## Objective

Define the resolver boundary that follows the semantic validation of
`AppearanceContribution` and precedes every future domain algorithm.

The purpose is not to implement COLOR, MATERIAL, LIGHTING, TRANSMISSION,
REFLECTION, EMISSION or BASE algorithms. The purpose is to make the transaction
between a validated domain payload and a future domain resolver explicit,
immutable, deterministic and auditable.

## Boundary

```text
AppearanceContribution
        ↓
Domain Contract Validation
        ↓
DomainResolutionInput
        ↓
future domain resolver
        ↓
DomainResolutionResult
        ↓
validated domain fields + provenance + dependency identity
```

One `DomainResolutionInput` owns exactly one rendering appearance domain. `STATE`
and `EFFECT` are excluded because their contracts already belong to their existing
resolution systems.

## Input contract

`DomainResolutionInput` contains:

- `target_id`: exact resolution target;
- `domain`: exactly one of BASE, MATERIAL, COLOR, LIGHTING, TRANSMISSION,
  REFLECTION, EMISSION;
- `contributions`: zero or more contributions, all belonging to that domain;
- `active_states`: canonicalized state names supplied by upstream resolution;
- `dependencies`: explicitly named SHA-256 content identities;
- `resolver_id` / `resolver_version`: explicit implementation identity;
- `contract_version`: semantic contract identity.

The constructor re-validates contributions through the existing appearance domain
contracts. This prevents a caller from bypassing the previous validation gate by
constructing a domain input directly.

## Output contract

`DomainResolutionResult` contains:

- exact target/domain ownership;
- explicit lifecycle status: `UNRESOLVED`, `RESOLVED`, `PARTIAL`, `REJECTED`;
- the exact input digest consumed by the resolver;
- explicit resolver identity/version;
- zero or more `DomainResolvedField` values;
- explicit unresolved reasons for partial/unresolved outcomes;
- provenance for successful/partial resolution;
- dependency digest.

A `DomainResolvedField` can only use a field declared by the same domain's
existing `DomainContract`. The resolver therefore cannot create a second,
parallel vocabulary at its output boundary.

## Fail-closed invariants

1. A rendering resolver cannot receive STATE or EFFECT.
2. A resolver input cannot mix domains.
3. Contribution IDs are unique.
4. Contributions are revalidated against the existing domain contract.
5. Dependency names and digests are explicit and deterministic.
6. A result from another target, domain, input digest or resolver identity is rejected.
7. Unknown output fields are rejected.
8. Output field values are revalidated against the domain contract.
9. Resolved/partial results require provenance.
10. Partial results require explicit unresolved reasons.
11. Unresolved/rejected results cannot contain resolved fields.
12. No operation mutates the input contribution data.
13. No color mixing, lighting, shading, optical calculation or renderer behavior is
    performed by this boundary.

## Determinism and invalidation

`DomainResolutionInput.input_digest` fingerprints the complete immutable input
including contributions, states, dependencies and resolver/contract identity.

`DomainResolutionResult.result_digest` fingerprints the complete result envelope.
The dependency digest is derived from the exact ordered dependency set. A change
in an upstream dependency therefore produces a different input identity rather
than relying on a manually maintained revision counter.

This gives the future cache/invalidation layer a stable identity without coupling
it to the implementation details of a particular domain algorithm.

## Provenance

`DomainResolutionProvenance` records:

- target;
- domain;
- contribution IDs;
- dependency names;
- resolver identity/version.

The provenance set must match the input exactly. This prevents a resolver from
claiming that a result came from a different contribution/dependency set.

## Deliberately not implemented

This checkpoint does **not** define:

- how a base color is composited;
- how a material responds to light;
- how palettes are generated;
- how light transport is calculated;
- Fresnel equations;
- refraction;
- absorption simulation;
- reflection models;
- emission/bloom;
- tone mapping;
- rasterization;
- renderer-specific output.

Those are domain algorithms and must be implemented only after their individual
semantic contracts are sufficiently precise.
