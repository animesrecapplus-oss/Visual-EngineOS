# V1.3 — MATERIAL Domain Resolution

## Objective

Provide the first concrete resolver for the `MATERIAL` appearance domain after
semantic validation and the generic domain resolver contract.

## Scope

The current MATERIAL contract declares these fields:

- `name` — string;
- `roughness` — finite numeric value validated by the existing contract;
- `metallic` — finite numeric value validated by the existing contract;
- `transmission` — finite numeric value validated by the existing contract;
- `emission` — finite numeric value validated by the existing contract.

This resolver treats one non-empty opaque MATERIAL contribution as one
**authoritative material record** and copies its declared fields into the generic
`DomainResolutionResult`.

## Why the algorithm is intentionally narrow

The current contracts do not define:

- precedence between multiple MATERIAL contributions;
- averaging or weighted blending of material parameters;
- physical coupling between metallic, roughness and reflection;
- energy conservation;
- Fresnel evaluation;
- transmission/refraction solving;
- emission accumulation;
- defaults for omitted fields;
- underlay semantics for translucent contributions.

The resolver therefore does not invent any of those rules.

## Resolution rules

1. Input domain must be `MATERIAL`.
2. Zero contributions → `REJECTED` (`MATERIAL_NO_AUTHORITY`).
3. More than one contribution → `REJECTED` (`MATERIAL_MULTIPLE_AUTHORITIES`).
4. One empty contribution → `REJECTED` (`MATERIAL_EMPTY_AUTHORITY`).
5. Contribution opacity different from `1.0` → `REJECTED` (`MATERIAL_TRANSLUCENT_AUTHORITY`).
6. One non-empty opaque contribution → `RESOLVED`.
7. Returned fields are copied without numeric transformation or invented defaults.
8. Output is validated again by the generic domain-resolution contract.
9. Provenance identifies the authoritative contribution and dependencies.

## Important distinction

A partial field set is not reported as `PARTIAL` here. The existing MATERIAL
contract does not declare required fields, so there is no objective completeness
criterion from which to derive that status. A non-empty validated record is
therefore `RESOLVED` as an authoritative **record**, not as a claim that every
possible material property is known.

## Determinism and invalidation

The input digest, resolver identity/version, dependency digest and provenance are
retained through the existing immutable result contract. Any change in the input
or declared dependency changes the corresponding identity rather than allowing a
stale result to masquerade as current.

## Explicit non-claims

This checkpoint does not implement material shading, BRDFs, lighting, reflection,
transmission, refraction, texture sampling, renderer integration, or multi-source
material composition.
