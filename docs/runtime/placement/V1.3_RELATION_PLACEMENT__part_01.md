# V1.3.6 — Relation → Placement → Semantic Target Resolution

**Status:** IMPLEMENTED — explicit graph-relation integration foundation.

## Objective

The previous V1.3.5 placement solver accepted a `PlacementIntent` directly. That
was deliberately isolated: it proved the geometry-to-geometry solver without
inventing a relation language.

This checkpoint adds the missing architectural connection:

```text
Relation
   ↓
validated placement declaration
   ↓
PlacementIntent
   ↓
Target Semantic Region (optional, explicit)
   ↓
Attachment / dimension / coverage / depth constraints
   ↓
Spatial Placement Solver
   ↓
PlacementSolution
   ↓
Visibility Kernel
```

The relation layer is still generic. It does not contain object-category logic.

## Explicit relation contract

A relation may contain a `metadata["placement"]` mapping. The following keys are
currently allowed:

- `source_anchor`
- `target_anchor`
- `target_region_id`
- `target_anchor_scope` (`component` or `region`)
- `rotation_deg`
- `offset_x`, `offset_y`
- `scale_mode`
- `width_ratio`, `height_ratio`
- `coverage`
- `coverage_tolerance`
- `coverage_max_iterations`
- `depth_relation`
- `depth_offset`

Unknown keys are rejected. This is intentional: a misspelled placement parameter
must not silently alter geometry.

Only the current spatial/attachment/geometric/contact/occlusion relation families
may carry a placement declaration. Other relation types fail closed if they try to
use this contract.

A relation without a placement declaration is not converted into an implicit
placement request.

## Semantic target selection

A placement may explicitly name a `target_region_id`.

The target geometry used by the placement solver is then that region's geometry,
not the whole target component.

Two anchor scopes are supported:

### `component`

The named target anchor must explicitly exist on the target component. The region
provides the geometry while the component supplies that declared reference point.
No center or other anchor is inferred.

### `region`

The named target anchor must explicitly exist on the selected semantic region.
No fallback to a component anchor is performed.

This distinction is important because a semantic region may have different geometry
from the component as a whole, while its attachment reference may legitimately be
owned by either the component or the region.

## Coordinate-frame boundary

`resolve_graph_placements()` requires the supplied source and target geometries to
already share a coordinate frame. It does not silently apply camera or scene
transforms.

The established transform pipeline remains the explicit boundary:

```text
component-local geometry
        ↓
local → world → scene → camera
        ↓
common-frame placement inputs
        ↓
placement solver
```

This prevents hidden double transforms and keeps placement renderer-independent.

## Why this is not an object-specific solver

There is deliberately no code equivalent to:

```python
if eye: ...
if glasses: ...
if hair: ...
if hand: ...
```

The same relation contract can describe any source/target pair as long as their
geometry and explicit anchors/regions satisfy the declared constraints.

For example, a future prompt compiler may produce a relation whose source is one
component and whose target is an eye-region component. The placement layer does
not need to know that either endpoint represents an eye, hair, hand or accessory.

## Relation identity and determinism

`Relation` does not yet contain a dedicated persisted ID. The integration therefore
uses a stable digest of the relation endpoints, type and metadata as the current
relation identity for resolution output and deterministic ordering.

This is deliberately not treated as a permanent database identity. A future
persistence schema may introduce an explicit relation ID once that contract is
stable.
