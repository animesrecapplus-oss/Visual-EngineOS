# V1.3.7 — Hard Spatial Placement Constraints

**Status:** IMPLEMENTED — deterministic hard-constraint layer; no general optimizer.

## Purpose

V1.3.6 connected graph relations to `PlacementIntent` and semantic target regions.
That layer resolved an affine placement from explicit anchors, dimensions, rotation,
offset, coverage and depth. The next missing boundary was the ability to state and
enforce additional geometric conditions without embedding object-specific rules.

This checkpoint adds explicit hard predicates:

```text
Relation
  ↓
Placement declaration
  ↓
PlacementIntent
  ↓
Target semantic region
  ↓
Analytic affine placement
  ↓
Hard geometric constraints
  ↓
PlacementSolution / explicit failure
```

## Implemented constraints

### Containment

The placed source footprint must lie inside the target footprint, within an explicit
area tolerance.

### Clearance

The minimum Euclidean distance between the placed source and target footprints must
be at least the declared distance, within tolerance.

### Non-penetration

The placed source and target footprints may not overlap in area beyond the declared
tolerance.

These constraints are evaluated on actual geometry, not bounding-box approximations.

## Deliberate non-goals

This layer does **not** implement a generic numerical optimizer. It does not invent
weights or silently trade one constraint against another.

It also does not yet implement:

- arbitrary orientation/alignment frames;
- surface-normal alignment;
- contact manifolds;
- collision response;
- penetration correction;
- directional language (`above`, `inside`, `left of`, etc.) as a prompt language;
- soft/statistical/aesthetic optimization;
- 3D constraints.

If a uniquely specified affine placement violates a hard constraint, resolution
fails explicitly. This is intentional and is a quality gate against plausible but
incorrect geometry.

## Relation integration

`metadata["placement"]["constraints"]` is now a closed schema containing only:

```text
containment
clearance
non_penetration
```

Unknown constraint names and malformed payloads fail closed.

A graph relation that declares hard constraints is validated by the normal
`resolve_relation_placement()` path; constraints are therefore not silently ignored
when graph-wide placement resolution is used.

## Materialization boundary

`resolve_placed_geometry()` converts a `PlacementSolution` into a new
`GeometryContract` using the existing affine transform contract.

Placement does not own scene/camera composition. The boundary remains:

```text
relation placement
    ↓
placed local/common-frame geometry
    ↓
local/world/scene/camera composition
```

No hidden camera transform is introduced by placement.

## Numerical policy

The solver remains deterministic:

- analytic affine placement for anchor/scale/rotation;
- explicit geometric predicates for hard constraints;
- fixed tolerances supplied by the caller or schema defaults;
- no random search;
- no unconstrained fallback;
- no silent correction of an unsatisfied hard constraint.

## Dependency and cache implications

The constraint set is part of placement semantics. A future placement dependency
fingerprint must include the canonical constraint declaration. Geometry cache keys
must not be invalidated merely by a constraint that is evaluated after geometry
construction; however, a changed constraint can invalidate the resolved placement
artifact and all downstream visibility/composition results.

This checkpoint does not yet add that fingerprint because the existing geometry
cache is deliberately scoped to generated geometry, not placement results.
