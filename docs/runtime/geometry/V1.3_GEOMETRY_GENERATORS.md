# V1.3 — Geometry Generator Contract & Registry

## Purpose

This checkpoint establishes the missing boundary between component semantics and the
production geometry cache.

```text
Component
  -> Generator Registry
  -> Geometry Generator
  -> GeometryContract
  -> GeometryCache
  -> Renderer
```

A generator is deterministic and renderer-neutral. It must return a
`GeometryContract`; it must never return SVG, pixels, or renderer-specific objects.

## Contract

Each registered generator exposes:

- `name`: stable logical generator identifier
- `version`: generator implementation boundary for cache invalidation
- `kinds`: supported component kinds
- `supports(component)`
- `cache_inputs(inputs)`: projection containing only geometry-affecting inputs
- `generate(component, inputs) -> GeometryContract`

`cache_inputs()` is deliberate: generator requests may contain visual data needed by
a renderer, but visual-only changes must not rebuild geometry.

## Registry rules

- one default generator per component kind
- generator names are globally unique
- explicit generator selection is supported
- unsupported component/generator pairs fail explicitly
- registry ordering is deterministic

## Eye implementation

The canonical generator is:

```text
face.eye v1
```

It adapts the existing `build_eye_geometry()` solver into `GeometryContract`.

The contract contains:

- aperture path
- upper/lower lid paths
- upper/lower crease paths
- iris primitive
- pupil primitives
- reflection primitive
- semantic surfaces
- stable anchors
- local bounds

The existing eye solver remains the domain geometry authority. The adapter is the
boundary into the generic engine; this avoids duplicating ocular mathematics.

## Cache semantics

The eye path is now:

```text
CachedGeometryGenerator
      |
      +-- registry.for_component("eye")
      |
      +-- generator.cache_inputs(inputs)
      |
      +-- GeometryCache.make_key(...)
      |
      +-- generator.generate(...) on MISS only
```

Therefore:

- gaze changes -> geometry MISS
- morphology changes -> geometry MISS
- eyelid crease geometry changes -> geometry MISS
- pupil geometric shape changes -> geometry MISS
- sclera color -> geometry HIT
- outline color -> geometry HIT
- lash color/style -> geometry HIT
- eyebrow styling -> geometry HIT
- glow/smoke visual settings -> geometry HIT

This separation is the required foundation for the later generic renderer pipeline.

## Deliberate scope boundary

The current eye generator does not claim that every eye visual detail is already
geometry. Lash strokes, eyebrow strokes, iris micro-patterns, smoke and glow remain
visual-layer responsibilities in the existing renderer. When those systems receive
true geometry generators, they must register their own geometry-affecting inputs
rather than being silently folded into the eye cache key.
