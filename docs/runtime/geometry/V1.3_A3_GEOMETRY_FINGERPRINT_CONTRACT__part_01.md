# V1.3 — A3 Geometry Fingerprint Contract — 2026-09-15

## Purpose

A3 closes the geometry fingerprint identity contract that was introduced during the
geometry-cache checkpoint but was not yet declared definitive.

The important distinction is:

```text
local geometry-input identity
        != visual identity
        != world transform identity
        != renderer output identity
```

The geometry cache key remains responsible for combining the local fingerprint with
component identity, dependency identity, generator identity/version and the engine/schema/
resolution version boundary.

## What was already implemented before A3

The previous checkpoints already contained:

- `geometry_input_fingerprint()`;
- `geometry_dependency_fingerprint()`;
- authored `Component.geometry` in the local fingerprint;
- generator-declared cache inputs;
- relation `geometry_inputs`;
- generator/version cache boundaries;
- a renderer-neutral `GeometryCache`;
- reverse dependency invalidation;
- deterministic SHA-256 geometry output hashes.

A3 therefore does **not** replace the existing cache. It closes the missing contract around
canonical identity, accepted input types, explicit exclusions and version evolution.

## Definitive local fingerprint payload

`geometry_input_payload()` now produces a versioned envelope:

```text
contract_version
algorithm
component
  kind
  parameters
  anchors
  constraints
  profiles
  state
  geometry
inputs
```

The following are deliberately excluded from the local geometry payload:

- `Component.id` — already carried by `GeometryCacheKey.component_id`;
- `appearance` — visual domain unless a generator explicitly projects a geometry-relevant
  value into its cache inputs;
- `visual`;
- `visual_overrides`;
- `transform` — geometry is generated in the component/local frame; placement is a later
  transform/composition concern.

This is an explicit boundary, not an accidental omission.

## Generator-derived inputs

A generator may derive geometry-relevant inputs from another domain. It must expose those
inputs through its `cache_inputs()` projection. The eye generator already follows this rule:
its cache projection retains geometry-changing pupil, iris, eyelid, gaze, state and expression
fields while excluding purely visual color/opacity/style fields.

This prevents a generic fingerprint from guessing which application-specific appearance
fields alter geometry.

## Canonicalization and rejection policy

Fingerprint inputs accept only deterministic data forms:

- `None`, `bool`, `str`, `int`;
- finite `float`;
- `Enum` values whose values are themselves supported;
- dataclasses whose fields are supported;
- mappings with **string keys** and supported values;
- lists/tuples containing supported values.

The boundary rejects:

- non-finite floats;
- sets and other unordered containers;
- arbitrary objects/repr-based identity;
- non-string mapping keys;
- cyclic containers/dataclasses.

Mapping order is canonicalized by the existing `stable_digest()` implementation; sequence
order remains significant because ordered geometry data can change generated geometry.
Python's process-randomized `hash()` is never used. Python's `hashlib.sha256` is used for the
final digest; SHA-256 is a deterministic byte digest API provided by Python's standard
library. citeturn0search0

## Dependency fingerprint

The dependency fingerprint now carries the same explicit fingerprint contract version and
algorithm marker. It contains:

- ordered target/ancestor geometry-input fingerprints;
- relation topology touching the relevant dependency closure;
- explicit `metadata["geometry_inputs"]`;
- relation-dependent component geometry-input fingerprints;
- additional generator-declared dependencies.

Visual-only relation effects remain outside the geometry identity. A relation that actually
changes geometry must declare its geometry data explicitly.

## Cache correctness matrix

A3 tests all declared local geometry inputs individually and verifies the important exclusions:

| Change | Geometry local fingerprint |
|---|---|
| component kind | changes |
| parameters | changes |
| anchors | changes |
| constraints | changes |
| profiles | changes |
| state | changes |
| authored geometry | changes |
| explicit generator inputs | changes |
| appearance-only data | unchanged |
| visual contract | unchanged |
| visual overrides | unchanged |
| local/world transform | unchanged |
| component ID | unchanged locally; cache key remains different |

The component-ID distinction is deliberate: two components may share the same local geometry
recipe while still requiring separate cache identities.

## Evolution boundary

The contract is explicitly versioned as `1` and identifies SHA-256 as its digest algorithm.
Changing the contract semantics requires incrementing the contract version. Because the version
is inside both the local and dependency fingerprint payloads, old cache identities cannot be
silently reused under a changed contract.
