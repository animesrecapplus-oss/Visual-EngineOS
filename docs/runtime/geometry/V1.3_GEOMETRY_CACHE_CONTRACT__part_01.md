# V1.3 — Production Geometry Cache Contract

## Purpose

The geometry cache stores **renderer-neutral `GeometryContract`** results. It is not an
SVG/raster cache and it is not a PostgreSQL render loop. The same geometry may therefore
feed SVG, CPU raster and future GPU backends.

## Cache identity

A geometry entry is identified by:

```text
component_id
+ geometry dependency fingerprint
+ local geometry-input fingerprint
+ generator id
+ generator version
+ engine/schema/resolution VersionStamp
```

The geometry dependency fingerprint is deliberately narrower than the visual-resolution
fingerprint. Changes to fill color, contour, shadow, tint, opacity or other visual-only
effects must not force a geometry rebuild.

### Local geometry inputs

The definitive identity rules are closed by A3. See `docs/runtime/geometry/V1.3_A3_GEOMETRY_FINGERPRINT_CONTRACT__part_01.md` (split document; see adjacent parts).

By default the local fingerprint includes:

- component kind
- parameters
- anchors
- constraints
- profiles
- state layers
- authored geometry
- explicit generator cache inputs

It excludes visual contracts, appearance colors, visual overrides and world transforms.
The component ID is carried separately by `GeometryCacheKey`. A generator must explicitly
project any geometry-relevant value derived from another domain into its cache inputs.

### Fingerprint canonicalization

The fingerprint contract is versioned (`1`) and uses SHA-256. Accepted values are finite
numbers, strings, booleans, null, enums, dataclasses, string-keyed mappings and ordered
lists/tuples. Unordered containers, arbitrary objects, non-string mapping keys, non-finite
floats and cyclic values are rejected before hashing. This prevents cache identity from
depending on process-specific object representations or unordered traversal.

## Cross-component dependencies

The dependency set follows the V1.3 relation contract:

```text
ancestors(target)
+
transitive semantic relation dependencies
+
ancestors(relation dependencies)
```

Relation topology is part of the geometry dependency fingerprint. Visual effect metadata
is not. A relation may provide geometry-specific metadata through:

```python
metadata={"geometry_inputs": {...}}
```

This avoids rebuilding geometry for a pure effect change while still allowing contact,
deformation, attachment and other geometry parameters to participate in the key.

## Invalidation

Entries keep a reverse dependency index:

```text
changed component
      ↓
reverse dependency index
      ↓
affected cache keys
      ↓
selective invalidation
```

No global cache flush is required for a local component change.

The key itself remains the final correctness guard: if a graph is rebuilt and its
fingerprint differs, the old entry cannot be returned even if explicit invalidation was
not called.

## Concurrency

`get_or_build()` uses per-key single-flight behavior:

- first caller becomes the builder;
- concurrent callers wait for that key only;
- successful build is published once;
- builder failures are propagated to waiters and never cached.

The global lock is not held while geometry is being built.

## Bounds / eviction

The cache is bounded by either or both:

- maximum entry count;
- deterministic serialized payload byte budget.

Eviction is LRU. An entry larger than the byte budget is not retained.

## Observability

`GeometryCacheStats` exposes:

- hits
- misses
- builds
- evictions
- explicit invalidations
- current entry count
- current accounted bytes

`GeometryCacheEntry` exposes the stable geometry digest and dependency IDs for audit.

## Non-goals of this checkpoint

This checkpoint does **not** yet claim:

- persistent geometry blobs in PostgreSQL;
- cross-process shared cache;
- disk cache;
- renderer output caching;
- automatic registration of every future geometry generator;
- geometric occlusion itself.

Those are separate architectural steps. The cache is intentionally established first as
a deterministic runtime boundary.
