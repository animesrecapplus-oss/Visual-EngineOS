# V1.3 — Semantic Regions & Partial Coverage Contract

**Status:** implemented foundation / not production-complete visibility

## 1. Why this phase exists

The engine must never reduce occlusion to `eye.visible = false` or to rules such as
"hand hides eye". An arbitrary geometric object can cover only part of a target,
from any direction and at any angle. The affected result must be determined from
space first, then mapped to semantic regions.

Permanent rule:

```text
GEOMETRIC INTERACTION
        ↓
where does it intersect?
        ↓
SEMANTIC MAPPING
        ↓
which regions are affected?
        ↓
STATE / EFFECT CONSEQUENCES
        ↓
APPEARANCE
        ↓
RENDER
```

The occluder has no knowledge of the target's component vocabulary.

## 2. SemanticRegion

`runtime/semantic_regions.py` introduces:

- `SemanticRegion`
- `RegionMap`
- `RegionKind`
- rectangle/polygon construction helpers

A region is geometry plus semantic identity. It does not encode that the region is
an eye, eyelid, finger, shirt, etc. The owner supplies the semantic name.

Example:

```text
RegionMap(target="eye")
├── upper_eyelid   → geometric region
├── iris           → geometric region
├── pupil          → geometric region
├── sclera         → geometric region
└── lower_eyelid   → geometric region
```

This permits future target types to expose arbitrary region maps without changing
the occlusion engine.

## 3. Occluder

`runtime/coverage.py` introduces a generic `Occluder`:

```text
occluder_id
geometry
z
opacity
transmission
metadata
```

There is intentionally no field such as `occluder_type="hand"` and no hardcoded
list of possible occluders.

The same kernel can therefore process a hand, hair strand, hat, weapon, glass,
leaf, another character, or an arbitrary generated shape.

## 4. Partial coverage

`resolve_coverage()` computes, for each semantic region:

- geometric coverage ratio;
- remaining geometric visibility;
- transmitted visibility contribution;
- depth relation.

It therefore answers questions such as:

```text
Occluder covers upper-left of target

upper_eyelid   62% covered
iris           18% covered
pupil           0% covered
sclera         31% covered
lower_eyelid    0% covered
```

The engine does not infer these values from object names. They come from geometric
intersection between the occluder and region geometry.

## 5. Depth, opacity and transmission are separate

These concepts must not be collapsed:

```text
GEOMETRIC COVERAGE ≠ OPACITY ≠ TRANSMISSION ≠ DEPTH
```

A region can be geometrically covered while still allowing transmitted visibility.
An object behind the target can intersect in 2D but cannot occlude it.

## 6. Current geometric kernel

The foundation currently supports:

- polygon primitives;
- ellipse/circle primitives through deterministic polygonization;
- arbitrary translations/rotations already supplied by the transform/composition
  stage;
- partial intersections at arbitrary spatial positions and diagonal orientations;
- depth classification.

The polygon clipping kernel is exact for convex polygon-vs-convex polygon
intersection. Ellipses are approximated by a configurable deterministic polygon.

This is deliberately **not** claimed to be a production boolean-geometry engine.
Concave multi-shape union, exact Bézier clipping, multi-occluder visibility,
subpixel raster visibility and optical effects remain future work.

## 7. Architectural boundary

This phase does not implement:

- hand-specific occlusion rules;
- eye-specific hiding rules;
- anatomical consequences;
- expression inference;
- material shading;
- color intelligence;
- physical transparency/refraction;
- final renderer clipping.

Those belong to subsequent resolvers.
