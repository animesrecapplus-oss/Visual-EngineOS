## 7. Appearance boundary audit

The next new component exposed an important question: should V1.46 create a bridge from legacy
`AppearanceLayer` payloads into the generic `VisualContract`?

The answer is no.

The generic resolver already exposes a typed inheritance mechanism through `VisualOverrides`.
A new component can explicitly inherit the parent's fill/contour/material/opacity/visibility by
using `VisualOverrides()` with all fields `None`.

The nose uses exactly that mechanism in:

`src/visual_engine/entities/face.py:24–31`

```python
nose.visual_overrides = VisualOverrides()
```

This makes the nose inherit the authored HumanFace skin presentation without duplicating a second
color authority.

The old `AppearanceLayer` payloads are heterogeneous. Existing examples include:

- linear-sRGB `base_color` arrays;
- contour strings and component-relative widths;
- procedural pattern markers;
- specular effect descriptors.

Automatically translating those values into `VisualContract` would require a new authority and
new precedence rules. V1.46 has no real consumer requiring that bridge.

> **V1.46 decision: use the existing generic inheritance contract; do not create a speculative
> legacy appearance bridge.**

## 8. Exactly one new HumanFace geometry family: Nose

### 8.1 Why Nose

The `HumanFace` builder already contains a `Nose` child and an `exactly_one_nose` hard constraint.
The generic geometry generator registry already supports component-kind dispatch and recursive
geometry dependencies.

Nose therefore has an existing component identity and an existing production tree location.
Only the geometry producer was missing.

Mouth, ears and hair were deliberately not added.

### 8.2 Generator identity

`src/visual_engine/components/face/generators.py:20–23` introduces:

- `FACE_WITH_EYES_NOSE_GEOMETRY_GENERATOR = "face.human_with_eyes_nose"`;
- `FACE_WITH_EYES_NOSE_GEOMETRY_GENERATOR_VERSION = "1"`;
- `NOSE_GEOMETRY_GENERATOR = "face.nose"`;
- `NOSE_GEOMETRY_GENERATOR_VERSION = "1"`.

### 8.3 Nose geometry

`src/visual_engine/components/face/generators.py:231–296` creates:

- one closed silhouette path;
- one left nostril cubic curve;
- one right nostril cubic curve;
- `NOSE` and `NOSE_DETAIL` semantic surface labels;
- `center` and `tip` anchors;
- explicit width and height parameters.

The geometry is renderer-neutral.

It does not contain:

- RGB operations;
- shading algorithms;
- texture algorithms;
- masks;
- boolean geometry;
- renderer-specific SVG strings.

### 8.4 Composite dependency

`src/visual_engine/components/face/generators.py:307–371` declares the exact dependency set:

```text
left_eye
right_eye
nose
```

The existing `CachedGeometryGenerator` recursively resolves these dependencies, so the nose is
not rendered through a special renderer path. It participates in the same cache and generator
contracts as the eyes.

### 8.5 Production default

`src/visual_engine/runtime/production_slice.py:91–115` changes the production request default to:

`face.human_with_eyes_nose`

The original `face.human_with_eyes` generator remains registered as an explicit alternative.
This preserves the older geometry contract while making the real production request consume the
new family.

### 8.6 Cache cardinality

The first production request now builds four geometry entries:

1. left eye;
2. right eye;
3. nose;
4. face composite.

Visual QA observed exactly four geometry builds.

## 9. Visual self-critique and correction

This was not accepted from mathematical validity alone.

### 9.1 First nose attempt — rejected

The first generated silhouette was too long and leaf-like. Although its path was valid,
finite and renderer-neutral, it did not produce a convincing readable stylized nose in the actual
face.

It was therefore rejected rather than certified.
