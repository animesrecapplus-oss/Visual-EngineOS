### Complexity

The nose dependency is one additional declared geometry dependency in the composite. It is
resolved through the existing recursive `CachedGeometryGenerator` path; no second orchestration
algorithm was added.

Visibility filtering is O(number of emitted geometry owners/primitives) after generic resolution.
It does not perform polygon boolean operations and therefore does not accidentally turn every
render into an occlusion solve.

## 22. What is still intentionally incomplete

The following are **not** claimed as V1.46 features:

- full nose morphology;
- mouth geometry;
- ear geometry;
- hair geometry;
- hand/object occlusion;
- boolean-mask rendering;
- automatic occluder inference from SVG order;
- persistent cache storage;
- cache partitioning;
- new cache byte budget;
- generic legacy `AppearanceLayer` conversion;
- new COLOR transformation.

This list is important because the generated face can look more complete than the engine actually
is. The implementation and evidence deliberately stop at the proven boundary.

## 23. Next step — V1.47 micro-scope in detail

V1.47 should now use the existing renderer-independent visibility machinery rather than inventing
another occlusion abstraction.

### Micro-step 1 — select one overlap

Choose one component pair that actually overlaps in the production face. The candidate must have:

- existing component identity;
- existing geometry contract;
- existing semantic-region representation or a direct generic region representation;
- explicit depth relation;
- a visually meaningful before/after result.

Do not choose a component solely because it is convenient to code.

### Micro-step 2 — materialize semantic regions

For both target and occluder, materialize the exact production geometry into a common frame.
Verify:

- coordinate frame;
- transform;
- scale;
- bounds;
- region area;
- depth.

### Micro-step 3 — call the existing visibility kernel

Use the repository's existing visibility/coverage contract. Do not create a second boolean or
occlusion engine.

The result must expose:

- coverage;
- visible fraction;
- blocked area;
- dominant occluder;
- depth relation;
- event provenance.

### Micro-step 4 — compare semantics with rendered pixels

Generate a before/after production SVG/PNG pair.

The visual result must agree with the semantic visibility result. A mathematically valid
intersection that produces the wrong visible pixels is a failed implementation.

### Micro-step 5 — measure cost

Measure visibility resolution on the real geometry before adding a visibility cache. If it is
fast enough, do not cache it merely because a cache exists elsewhere.

### Micro-step 6 — repeat lifecycle gates

Re-run:

- multiple live sessions;
- shared cache lifetime;
- undersized cache pressure;
- stale graph;
- parameter invalidation;
- teardown;
- deterministic fresh-session SVG;
- fail-closed behavior;
- visual regression;
- COLOR regression.

### Micro-step 7 — only then select another face family

A second missing HumanFace family should wait until the first real overlap/visibility path has
been proven.

## 24. Final V1.46 conclusion

V1.46 is complete because the first production slice now has a measured multi-owner lifetime,
real cache-sharing evidence, one concrete additional face geometry family, a generic appearance
inheritance consumer, and a real visibility effect in emitted production output.

It does **not** claim that the engine now has a complete face renderer or complete occlusion
system. Those claims would be false.

The current production frontier is precise:

```text
production generation/render slice
        ✓
multi-session ownership
        ✓
shared-cache evidence
        ✓
one additional face geometry family
        ✓
resolved visibility consumed
        ✓

next:
one real overlapping component pair
        ↓
semantic visibility + depth
        ↓
rendered-output agreement
        ↓
measured visibility cost
```

That is the boundary handed to V1.47.
