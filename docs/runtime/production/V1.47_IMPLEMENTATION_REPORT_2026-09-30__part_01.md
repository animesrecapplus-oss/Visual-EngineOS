# V1.47 — Implementation Report — 2026-09-30

## 1. Executive summary

V1.47 implements the next roadmap brick after V1.46: the first **real production visibility path**.
Before changing source code, the roadmap, current status, implementation log, decisions and V1.46
contract were read. They all pointed to the same next boundary: one genuine overlapping production
pair, existing visibility kernel consumption, semantic regions, explicit depth, visual comparison,
and performance measurement before any cache.

The selected pair is `HumanFace head <- Nose`.

No second face geometry family was added. The existing V1.46 nose is reused. The implementation
connects the real camera-space geometry generated by `ProductionRenderSession` to the existing
`resolve_visibility()` and `resolve_visibility_attribution()` kernels.

The critical engineering discovery was that the production head and nose are closed Bézier paths,
while the generic visibility kernel consumes area primitives. A naive global path-to-area change was
experimented with and rejected because it changed the meaning and cost of unrelated renderer paths.
The accepted solution is an explicit semantic-region bridge: only a surfaced closed path becomes a
polygon region.

The final result is visually consistent at 0°, +12° and -12°. The nose is fully inside the head,
the kernel reports ~1.2276% head coverage and ~98.7724% remaining visibility, and the raster IoU
between the blocked kernel region and the exact nose semantic region is 1.0 in all three samples.

The visibility hot path was then optimized. Median visibility resolution improved from
4,218,946.5 ns to 3,476,087.0 ns on the same workload, a measured improvement of ~17.61%.
No visibility cache was added.

Final repository matrix: 111 test files, 956 collected tests, 955 passed, 1 expected PostgreSQL
skip, 0 failed. `compileall` passes. COLOR runtime is byte-identical to V1.46.

## 2. Roadmap and vision verification

### 2.1 V1.46 completion was checked

V1.46 explicitly ended with a next micro-scope requiring:

- one real overlapping production component pair;
- existing renderer-independent visibility kernel consumption;
- semantic regions and explicit depth;
- blocked/visible/dominant/depth proof;
- comparison against actual rendered output;
- visual evidence;
- performance measurement before caching;
- lifecycle/cache/determinism/visual regression;
- preserved `ResolutionFingerprint.cache_identity`;
- frozen COLOR;
- no second face geometry family until overlap is proven.

Every item is addressed by this checkpoint. The implementation does not skip directly to mouth,
ear, hair, physical 3D depth or visibility caching.

### 2.2 Why head <- nose is the correct pair

The head is already a production surface in `face.human_with_eyes_nose`. The nose was already
introduced in V1.46. Their shapes overlap in the exact production camera-space output. Therefore
this pair is not a synthetic test-only overlap.

The pair also exposes a real architectural seam: the head and nose are renderer paths, not area
primitives. Solving that seam is directly relevant to future visibility work.

## 3. Pre-change architecture audit

The existing components were inspected before modification:

```text
build_human_face
  → RuntimeGraph.from_component
  → resolve_component + ResolutionCache
  → CachedGeometryGenerator
  → face.human_with_eyes_nose
  → resolve_geometry_contract
  → render_geometry_svg
```

The existing visibility stack already contained:

```text
SemanticRegion / RegionMap
Occluder / DepthRelation
resolve_visibility
resolve_visibility_attribution
PlacementVisibilityResolution
```

The missing production seam was therefore not another visibility algorithm. It was the explicit
conversion of real production surface geometry into the area representation expected by the
existing kernel, plus request-boundary ownership.

## 4. Rejected implementation: global path interpretation

The first implementation made `geometry_to_region()` automatically flatten every closed path.
Although the mathematics produced valid regions, this was rejected for two reasons.

First, a renderer path is not automatically a semantic filled area. An eyelid crease or other
closed-looking renderer path can have presentation semantics that are not an occluder.

Second, the full repository visibility suite became much more expensive because every unrelated
visibility operation started flattening closed paths. This violated the project's requirement to
avoid speculative work and to measure before optimizing.

The implementation was reverted to primitive-only generic region conversion. The path conversion
now occurs only at `generic_geometry_region_map()` for an explicitly surfaced closed path.

This is a concrete example of rejecting code that was mathematically correct but architecturally
wrong.

## 5. Final geometry bridge

### 5.1 `path_to_region()`

`runtime/visibility.py` now exposes a deterministic closed-path conversion function.

It accepts M/L/C/Q/Z sequences and samples quadratic/cubic segments deterministically. It validates
that the path starts with `M` and ends with `Z` and refuses unsupported commands.

The function is not used by the global `geometry_to_region()` path.

### 5.2 Semantic provider promotion

`runtime/region_maps.py` inspects `GeometrySurface.path_index` only when a surface explicitly exists.
A closed surface path is flattened, validated with Shapely and converted into polygon primitives.

The generated semantic region carries the original owner and path index as metadata.

Open nostril paths are deliberately ignored for area visibility. This prevents a decorative line
from becoming a zero-width or invented filled occluder.

### 5.3 Holes

The generic polygon primitive used by this region bridge has no hole field. Rather than dropping
holes, V1.47 rejects surfaced closed paths containing holes. This is intentionally conservative.
A future hole-capable semantic geometry contract can be added only when an actual production
consumer requires it.
