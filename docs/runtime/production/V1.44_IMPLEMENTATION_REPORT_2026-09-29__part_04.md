## 19. Final architectural conclusion

V1.44 does not justify adding another runtime abstraction.

The evidence instead establishes a concrete architectural gap:

```text
existing library contracts
        ≠
production-owned generation/render request
```

The project should therefore widen horizontally now.

The next implementation should create **one real production vertical slice**
for a single supported entity/component path rather than continue deepening
COLOR or cache orchestration in isolation.

That next slice must be small enough to validate the ownership model but real
enough to exercise actual generation and rendering.

# V1.45 — next implementation micro-scope

V1.45 should be the first **production-owned generation/render entry point**.
It is no longer a cache audit. The exact implementation must still be driven by
existing contracts rather than inventing a second engine.

### 1. Choose the smallest real production asset

Start with one already implemented entity/component family for which geometry,
appearance and renderer output exist. The eye/face path is the current strongest
candidate, but the final selection must be justified from the source graph rather
than assumed.

### 2. Define one explicit production request boundary

The boundary must own, explicitly:

- input component/entity identity;
- `RuntimeGraph` construction/reuse;
- appearance context;
- geometry-generation service/cache if needed;
- placement/camera inputs;
- renderer invocation;
- output artifact ownership;
- teardown.

No global singleton is allowed.

### 3. Decide generic resolution usage from evidence

If the selected production slice genuinely needs `resolve_component()`, wire it
through the real boundary and give it a caller-owned `ResolutionCache` only if the
measured request lifetime warrants it.

If the selected slice legitimately does not need generic resolution, document that
explicitly instead of forcing it into the path.
