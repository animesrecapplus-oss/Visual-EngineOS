## 1. Executive result

V1.44 was implemented as the next brick after the V1.43 finding that no
production caller owns generic resolution or `ResolutionCache`.

The purpose was not to keep expanding COLOR or to invent another cache layer.
The implementation instead traced the first plausible engine-wide production
entry path across the existing entity, runtime, geometry, spatial and renderer
surfaces.

The source audit covered **172 production Python files**.

Final finding:

```text
external production resolve_component() callers       0
external production resolve_component_contract() callers 0
production CachedGeometryGenerator owners             0
production renderer callers                           0
production entity-factory callers                     0
ambiguous audited star imports                         0
dynamic __import__/eval/exec calls                     0
scene -> runtime imports                                0
```

Therefore V1.44 correctly remains **audit-only**. No production orchestrator was
invented merely to make the architecture look more complete.

## 2. Why this is the correct next brick

The project has a large amount of infrastructure already present:

```text
entity factories
      ↓
Component / RuntimeGraph
      ↓
generic resolution
      ↓
geometry registry + cache
      ↓
spatial transform / placement / visibility
      ↓

```

But the audit demonstrates that these are currently separate library surfaces.
The repository has no production-owned request that connects them into one
runtime path.

This is a more important finding than adding another COLOR abstraction or cache
manager. It establishes the actual frontier of the engine rather than creating
architecture ahead of evidence.

## 4. AST audit design

### 4.1 Why plain grep was insufficient

A text search can confuse:

- a function definition with a consumer;
- an `__all__` export with an invocation;
- a compatibility wrapper with an external caller;
- a local helper call with a downstream owner;
- an import alias with an unrelated symbol.

The V1.44 scanner therefore parses Python syntax and separates those cases.

### 4.2 Alias resolution

The scanner records:

- direct imports;
- `from ... import symbol` imports;
- aliases such as `from ... import resolve_component as rc`;
- module aliases such as `import ...contract as contract`;
- direct call expressions;
- public `__all__` exports.

Calls made inside the module that defines the audited symbol are excluded from
the external-consumer count. This is what prevents
`resolve_component_contract()`'s internal compatibility call from becoming a
false production consumer.

### 4.3 Ambiguity checks

The scanner also checks for:

- star imports from audited modules;
- dynamic `__import__` calls;
- `eval` / `exec` calls.

The final source graph contains none of these ambiguity sources.

The scanner has no need to infer a hidden consumer from a string mention.

## 5. Actual production result

### 5.1 Generic resolution

`src/visual_engine/runtime/contract.py` defines and exports the generic resolver.

No other production module calls it.

The compatibility wrapper
`resolve_component_contract()` calls the resolver internally, but this is an
implementation relationship inside the same module, not an external owner.
