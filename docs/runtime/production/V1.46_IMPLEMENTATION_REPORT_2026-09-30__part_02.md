### 4.1 The defect

V1.45's `ProductionRenderSession.close()` always cleared its geometry and resolution caches.
That was correct only when the session had created those caches itself.

With two sessions sharing explicitly injected caches:

```text
Session A ─┐
           ├── caller-owned GeometryCache / ResolutionCache
Session B ─┘

A.close()
   ↓
cache.clear()
   ↓
B unexpectedly loses its live working set
```

This is a concrete lifetime bug, not a theoretical concern.

### 4.2 Implementation

`src/visual_engine/runtime/production_slice.py` lines 49–69 now distinguish ownership:

```python
self._owns_geometry_cache = geometry_cache is None
self._owns_resolution_cache = resolution_cache is None
```

Injected caches remain caller-owned.

`close()` lines 157–169 clears only caches whose ownership flags are true.

The code comments at lines 60–62 explicitly explain why this distinction exists.

### 4.3 Resulting contract

| Construction | Cache owner | `session.close()` |
|---|---|---|
| no cache supplied | session | clears cache |
| `geometry_cache=` supplied | caller | leaves cache intact |
| `resolution_cache=` supplied | caller | leaves cache intact |
| both supplied | caller | leaves both intact |

No global owner, reference-counting manager or process cache was introduced.

### 4.4 Regression coverage

`tests/unit/test_v146_production_slice.py`:

- lines 41–59: concurrent shared-cache sessions;
- lines 95–116: injected-cache lifetime after one session closes;
- lines 118–126: default session-owned cache teardown.

## 5. Real simultaneous cache workload

A dedicated benchmark uses the actual `ProductionRenderSession.render_face()` path in a
`ThreadPoolExecutor`. Four sessions remain alive simultaneously.

Tool:

`tools/benchmark_v146_multi_session.py`

Artifact:

`artifacts/v146_production_vertical_slice/V1.46_MULTI_SESSION_CACHE_BENCHMARK.json`

The workload renders each session for 20 rounds.

### 5.1 Healthy working set

The complete active workload requires 16 geometry/resolution keys.

| Mode | Geometry builds | Geometry hits | Evictions |
|---|---:|---:|---:|
| shared, 16 entries | 16 | 304 | 0 |
| partitioned, 16 entries | 16 | 304 | 0 |

Resolution has the same reuse cardinality: 16 stores, 304 hits, 0 evictions.

This is the important result: when the cache can hold the actual active key set, sharing does not
produce a correctness or reuse penalty.

### 5.2 Deliberately undersized working set

The same workload was run with only six entries per cache.

| Mode | Geometry builds | Geometry hits | Geometry evictions |
|---|---:|---:|---:|
| shared, 6 entries | 308 | 12 | 302 |
| partitioned, 6 entries | 16 | 304 | 0 |

The shared cache is demonstrably polluted because four sessions are cycling through more keys than
its capacity.

This does **not** justify a partitioning API yet. It demonstrates that cache capacity must be
considered before cache partitioning. Therefore:

> **V1.46 decision: no cache partitioning.**

The measured healthy-capacity behavior is identical between shared and partitioned storage, while
the undersized behavior is exactly what bounded LRU semantics predict.

### 5.3 Performance interpretation

The benchmark records wall-clock durations, but timing is diagnostic only. It is not used as a
release threshold because this workload is a structural cache/ownership experiment, not a stable
performance laboratory.

The semantic evidence is the deterministic build/hit/eviction cardinality.

## 6. Multi-instance memory measurement

A real production session is created and rendered for 1, 2, 4 and 8 simultaneously live sessions.

| Sessions | Geometry cache bytes | Resolution entries | tracemalloc current | tracemalloc peak |
|---:|---:|---:|---:|---:|
| 1 | 50,261 | 4 | 587,691 | 735,581 |
| 2 | 100,522 | 8 | 901,919 | 1,049,809 |
| 4 | 201,044 | 16 | 1,472,493 | 1,620,383 |
| 8 | 402,088 | 32 | 2,665,896 | 2,813,786 |

The geometry payload is approximately linear with the number of distinct live session keys.

No additional byte budget is introduced because the existing `GeometryCache.max_entries` /
`max_bytes` and `ResolutionCache.max_entries` already bound the explicit storage objects.

> **V1.46 decision: no new memory budget.**

The next memory question should be asked only when a real production workload exceeds the existing
bounds or when a measured retained-memory slope becomes operationally problematic.
