# V1.46 — Production Slice Strengthening Contract

**Date:** 2026-09-30  
**Status:** `ENGINEERING PASS — MULTI-SESSION OWNER / SHARED-CACHE LIFETIME / ONE NEW FACE FAMILY / VISIBILITY CONSUMED / VISUAL QA PASS / COLOR UNCHANGED`

## 1. Purpose

V1.46 strengthens the first real production path created in V1.45. The scope is deliberately
small and evidence-driven:

1. prove that more than one `ProductionRenderSession` can live at the same time;
2. distinguish session-owned caches from caller-injected shared caches;
3. measure shared versus partitioned cache behavior with real concurrent production requests;
4. measure multi-instance retained memory before considering a new byte budget;
5. inspect the appearance boundary and use the existing generic field-level inheritance contract
   where the new component actually needs it;
6. add exactly one missing `HumanFace` geometry family: `Nose`;
7. consume the nose through the same production generation/cache/transform/render path;
8. make resolved visibility affect emitted production SVG;
9. keep geometric occlusion attribution separate from renderer draw-order guesses;
10. repeat stale-graph, cache, teardown, determinism, fail-closed and visual gates.

The slice does **not** add mouth, ears, hair, a scene manager, persistent caches, cache
partitioning, a new byte budget, or a new COLOR transformation.

## 2. Production path

```text
build_human_face()
  → ProductionRenderSession
  → RuntimeGraph.from_component()
  → resolve_component() + ResolutionCache
  → CachedGeometryGenerator + GeometryCache
  → face.human_with_eyes_nose
       ├─ face geometry
       ├─ left eye geometry
       ├─ right eye geometry
       └─ nose geometry
  → resolve_geometry_contract()
  → resolve child VisualContracts
  → render_geometry_svg()
  → SVG
  → PNG evidence
```

The new nose is the only new geometry family in this chain.

## 3. Cache ownership contract

### 3.1 Default construction

When the caller omits both caches, `ProductionRenderSession` constructs them and owns their
lifetime. `close()` clears those caches.

### 3.2 Injected caches

When a caller injects `GeometryCache` and/or `ResolutionCache`, the caller owns those objects.
The session stores and uses them but does **not** clear them on `close()`.

This is required for multiple simultaneous sessions. Otherwise:

```text
session A ─┐
           ├─ shared cache
session B ─┘

A.close() → cache.clear() → B unexpectedly loses its live working set
```

V1.46 removes that lifecycle hazard without introducing a global manager.

### 3.3 Semantic cache identity

`ResolutionFingerprint.cache_identity` remains unchanged and remains the sole semantic
resolution-cache identity. No new session id, frame id, process id or partition token enters the
resolution key.

Geometry identity remains governed by the existing `GeometryCacheKey` and geometry fingerprints.

## 4. Shared versus partitioned workload evidence

The benchmark keeps four real sessions alive simultaneously and renders them concurrently.
Each session is a real `ProductionRenderSession.render_face()` caller.

Two capacities are measured:

- **16 entries:** the complete four-session workload requires 16 geometry/resolution keys;
- **6 entries:** deliberately undersized to expose LRU pollution.

Observed result:

| Workload | Geometry builds | Geometry hits | Geometry evictions |
|---|---:|---:|---:|
| shared, 16 entries | 16 | 304 | 0 |
| partitioned, 16 entries | 16 | 304 | 0 |
| shared, 6 entries | 308 | 12 | 302 |
| partitioned, 6 entries | 16 | 304 | 0 |

The evidence demonstrates a real capacity/pollution effect, not a semantic reason to partition
caches. At a capacity containing the active key set, sharing and partitioning produce the same
reuse counts. Therefore **no partitioning API is added in V1.46**.

The undersized result is retained as a regression warning: a future workload that exceeds the
working-set capacity must be treated as a capacity problem before it is treated as a cache
ownership/partitioning problem.

## 5. Multi-instance memory evidence

Real sessions were instantiated concurrently and each rendered one production face.

| Sessions | Geometry cache bytes | Resolution entries | tracemalloc current | tracemalloc peak |
|---:|---:|---:|---:|---:|
| 1 | 50,261 | 4 | 587,691 | 735,581 |
| 2 | 100,522 | 8 | 901,919 | 1,049,809 |
| 4 | 201,044 | 16 | 1,472,493 | 1,620,383 |
| 8 | 402,088 | 32 | 2,665,896 | 2,813,786 |

The retained geometry cache payload scales approximately with the number of live sessions and
active keys. No new global memory budget is justified by this workload because the existing
per-cache `max_entries` and `max_bytes` bounds already provide the relevant controls.

## 6. Appearance boundary audit

The existing generic resolver already provides an explicit field-level inheritance mechanism:
`VisualOverrides(None, ...)` means inherit the corresponding parent field.

The new nose is a concrete consumer of that contract:

```python
nose.visual_overrides = VisualOverrides()
```

The nose therefore inherits the authored `HumanFace` fill and contour without copying the skin
color into a second authority.

No renderer-side legacy `AppearanceLayer` parsing was added. This is important because the legacy
appearance payload contains heterogeneous historical values such as `base_color`, `pattern`,
`type`, and `strength`; blindly translating those fields into `VisualContract` would create a
false generic bridge.

The existing eye-specific appearance representation remains outside this generic slice. The
V1.46 requirement is satisfied by using the already-existing typed generic inheritance contract
where a new production component needs it, not by creating a speculative legacy-to-generic
converter.
