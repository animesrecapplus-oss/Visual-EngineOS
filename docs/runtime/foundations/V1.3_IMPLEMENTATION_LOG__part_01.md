# V1.3 Implementation Log

## V1.3 — MATERIAL Domain Resolution — 2026-09-15

**Status: implemented and verified.**

The second concrete appearance-domain algorithm is now present. MATERIAL is
resolved as one authoritative, non-empty, opaque material record. The resolver
reuses the generic domain input/result contracts and the existing closed MATERIAL
payload vocabulary; it does not create a parallel material model.

### What was implemented

- Added `resolve_material_domain()` and its input factory.
- Accepted exactly one non-empty opaque MATERIAL contribution.
- Rejected zero contributions, multiple contributions, empty contributions and
  translucent authority explicitly.
- Preserved every validated material field without averaging, summing, clamping,
  default insertion or physical transformation.
- Retained resolver identity, input digest, dependency digest and provenance.
- Revalidated the generated result through the generic domain-resolution contract.
- Added regression tests for normal resolution, partial field sets, determinism,
  fail-closed cardinality/opacity behavior and non-domain misuse.

### Why partial field sets are RESOLVED

The existing MATERIAL semantic contract declares no required fields. Therefore the
resolver cannot truthfully infer a completeness rule and does not label a valid
non-empty record `PARTIAL`. `RESOLVED` means that the supplied authoritative record
was resolved, not that every conceivable material property is known.

### Explicit nonclaims

No material composition, BRDF, Fresnel calculation, physical shading, lighting,
reflection/refraction solving, texture sampling, energy-conservation model or
multi-source precedence is implemented by this checkpoint.

## 2026-09-13 — Transform invariants + provenance + version/invalidation contract

### Starting artifact

Work started from `visual_engine_v1.3_resolution_hardening.zip`, not from a remembered description. The archive contains the previous V1.3 geometry/visual contract work.

### 1. Transform contract hardened

Added reusable mathematical helpers in `model.visual_contract`:

- `identity_matrix()`;
- `compose_matrices()`;
- `transform_point()`;
- `matrix_is_finite()`;
- `matrix_determinant()`.

The existing `LocalTransform.matrix()` remains the source of truth and continues to use `T·R·S` without decomposition.

Tests now verify identity, origin translation, negative-scale mirroring, rotation periodicity, determinant, associativity within tolerance, finite matrices, and deep-chain stability.

### 2. Structured resolution provenance

Added `runtime.provenance`:

- `ResolutionStep`;
- `ResolutionProvenance`.

`ResolvedComponent` now exposes structured provenance in addition to the legacy string trace. Each important visual field records where it came from and which policy produced the result. Transform, z, shadow and state policies are also recorded.

This is intentionally diagnostic data, not a semantic shortcut: unresolved future systems are not falsely reported as solved.

### 3. Version / invalidation identity

Added `runtime.versioning`:

- `VersionStamp`;
- `ResolutionFingerprint`;
- `component_fingerprint()`;
- `dependency_fingerprint()`;
- `context_fingerprint()`;
- `resolution_fingerprint()`;
- `InvalidationReason`;
- `invalidation_reasons()`;
- canonical `stable_digest()`.

The dependency fingerprint follows the complete target ancestor chain. A sibling modification therefore does not invalidate an unrelated target, while a target/ancestor modification does.

The correctness mechanism is content hashing, not a manually maintained revision counter. This is important because `Component` is currently mutable and nested structures can be changed directly.

`ResolvedComponent` now carries the version stamp and its resolution fingerprint, establishing the identity boundary required by a future cache.
