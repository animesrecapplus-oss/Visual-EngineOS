## V1.3 — A6 version policy stabilization — 2026-09-16

### Starting audit

A6 was explicitly checked before implementation. It was not complete. The repository
had conflicting version defaults: `pyproject.toml` declared `1.3.5`, package
`__version__` declared `1.0.0`, `VersionStamp.engine` declared `1.3.4`, while schema
and resolution defaults were `2` and `12`. Additionally, `canonical_entity_record()`
used the schema version as the default engine version.

### Implemented

- Created `src/visual_engine/runtime/version_policy.py` as the canonical owner of the
  three independent defaults: engine `1.3.5`, schema `2`, resolution `12`.
- Changed `VersionStamp` to consume those constants while preserving explicit overrides.
- Changed package `__version__` to consume `ENGINE_VERSION`.
- Corrected `canonical_entity_record()` so `engine_version` defaults to `ENGINE_VERSION`
  and `schema_version` defaults to `SCHEMA_VERSION`.
- Exported policy constants and `VersionPolicy` through the runtime package.
- Created `tools/verify_a6_version_policy.py` to detect source/package/pyproject drift
  and to assert that migration IDs remain a separate lifecycle.
- Created `tests/unit/test_v13_a6_version_policy.py`.
- Updated the persistence regression expectation.
- Updated the version/invalidation contract and master status history.

### Underestimated axes explicitly covered

1. **Packaging drift:** `pyproject.toml` is checked against runtime engine identity.
2. **Serialization drift:** engine and schema fields can no longer inherit the same
   default accidentally.
3. **Migration semantics:** migration operation IDs are deliberately kept separate
   from semantic schema versioning.
4. **Historical reproducibility:** explicit old `VersionStamp` values remain valid for
   compatibility/regression checks rather than being rewritten to current defaults.
5. **Public API exposure:** policy values are exported so callers do not need to copy
   literals.
6. **False-positive prevention:** the verifier does not require unrelated versions to
   be equal; it checks only ownership relationships that are semantically required.

## V1.3 — A7 generic PostgreSQL persistence vertical slice — 2026-09-16

### Audit before implementation

Inspected the A6 checkpoint's persistence implementation, all eight SQL migrations, existing migration
contract tests, entity round-trip API, ocular catalog API, and PostgreSQL-related roadmap/status claims.
The migration lifecycle was already implemented and was not duplicated. The actual A7 residue was the
absence of a generic `Component` graph persistence/hydration path.

### Implementation details

1. Added `persistence/serialization.py` to serialize and rehydrate renderer-neutral transform, visual,
   visual-override and geometry contracts while leaving queryable facts relational.
2. Extended `PostgresEntityRepository` with `save_component_tree()` and `load_component_tree()`.
3. Compiled `RuntimeGraph` before writes and after hydration so malformed hierarchy/relation topology
   fails closed rather than becoming persisted corruption.
4. Added entity-row locking before `entity_versions` version allocation; aggregate `FOR UPDATE` was
   deliberately avoided because PostgreSQL rejects row-locking an aggregate query.
5. Persisted sibling order explicitly in component metadata because SQL result order is not a semantic
   ordering guarantee.
6. Hydrated constraints/profiles/appearance/state/relation families with bounded queries instead of
   per-component database calls.
7. Added deterministic JSONB encoding with `allow_nan=False`, rejecting non-JSON Python values before
   they can enter the transaction.
8. Added offline verifier and regression tests covering serialization, bounded hydration, topology
   rejection and JSONB fail-closed behavior.
