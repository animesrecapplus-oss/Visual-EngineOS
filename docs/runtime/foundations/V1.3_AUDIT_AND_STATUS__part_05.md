### Pre-implementation audit

A5 was checked against the A4 checkpoint before adding code. The project already contained
`tools/qa_a0_closure.py` and a deterministic A0 closure manifest, so a second narrow brow/closed-eye
generator would have been duplicate work. However, the A5 requirement was broader: the historical
visual QA verdict named a complete feedback matrix whose reproduction script and manifest were absent
from the audited archive. A5 therefore restores the complete matrix and a strict verification gate.

### Implementation

Created:

- `tools/scripts_visual_qa_v13_feedback.py` — authoritative deterministic generator;
- `tools/verify_a5_visual_qa.py` — strict archive/reproducibility verifier;
- `tests/unit/test_v13_a5_visual_qa.py` — static integrity regression tests;
- `artifacts/history/v1.3/qa_feedback/manifest.json` — SHA-256 manifest for all generated SVG/PNG evidence;
- `artifacts/A5_EVIDENCE.txt` — execution evidence and source hashes.

The generator intentionally removes the old output directory before rendering. This prevents stale
files from previous runs from becoming invisible false positives. Each case fixes unrelated variables
where possible so visual differences remain attributable to the intended matrix axis.

The verifier checks, in order:

1. generator and verifier sources exist;
2. every archived SVG/PNG exactly matches the manifest;
3. the manifest is not self-referential;
4. a clean generation produces the same manifest twice;
5. that clean manifest equals the archived manifest;
6. the evidence records all strict gates.

### Coverage

The generated matrix contains **88 evidence files**: 44 SVG + 44 PNG, representing 44 controlled
visual cases. The matrix includes every currently public ocular morphology, gaze direction, lash form,
brow semantic variant and the previously documented reference/effect cases.

CairoSVG 2.8.2 was available in this execution environment. The verifier therefore checks both SVG

### Explicit nonclaims

A5 does not claim that the eye renderer is anatomically complete, that the reference-oriented presets
are pixel-identical reconstructions, or that hash reproducibility proves visual correctness. It proves
that the documented matrix can be regenerated deterministically from an archived source and that the
archived evidence matches its declared content identity.


## A6 — Version policy stabilization — 2026-09-16

### Pre-implementation audit

A6 was not already implemented. The audit found: `pyproject.toml` at `1.3.5`;
`visual_engine.__version__` at `1.0.0`; `VersionStamp.engine` at `1.3.4`;
`VersionStamp.schema` at `2`; `VersionStamp.resolution` at `12`; and
`persistence.schema.canonical_entity_record()` incorrectly using `SCHEMA_VERSION`
as its default `engine_version`. These are concrete drift points, not inferred gaps.

### Implemented

- Added one canonical `runtime.version_policy` containing independent engine, schema
  and resolution boundaries.
- Routed `VersionStamp()` through that policy.
- Routed package `__version__` through `ENGINE_VERSION`.
- Corrected entity serialization so `engine_version` and `schema_version` have separate
  defaults.
- Exported the policy through `runtime.__init__`.
- Added a strict verifier that checks source/runtime/package/pyproject consistency and
  explicitly preserves migration-ledger independence.
- Added regression tests for current defaults, package metadata, serialization and
  explicit historical version stamps.
- Documented the distinction between semantic schema version and PostgreSQL migration ID.

### Verification

`tools/verify_a6_version_policy.py`, full pytest, and compileall all pass. No live
No live PostgreSQL server is claimed verified by A6.

### Nonclaims

A6 does not merge engine/schema/resolution into one number, does not retroactively
rewrite historical version stamps, does not alter the resolution semantics (therefore
does not increment `RESOLUTION_VERSION`), and does not prove production deployment compatibility.

## A7 — Generic PostgreSQL persistence vertical slice — 2026-09-16

### Pre-implementation audit

A7 was not treated as a blank feature. The checkpoint already contained eight ordered SQL migrations,
a checksum-protected migration runner, `PostgresEntityRepository.save_entity/load_entity`, and an
ocular catalog lookup. Those pieces were retained. The audit identified the actual missing boundary:
there was no generic persistence path for the full `Component` authoring graph and no hydration proof
covering the relational component model.

### Implementation

Implemented `save_component_tree()` and `load_component_tree()` on the existing repository boundary.
The write path validates `RuntimeGraph` first, validates root kind/seed, serializes JSONB payloads with
`allow_nan=False`, locks the entity row before allocating the next immutable version, and writes the
entity/version/relational projection in one transaction. The load path performs bounded queries per
relation family, reconstructs all component contract fields, restores sibling order, validates
relations and recompiles `RuntimeGraph` before returning the graph.

The persistence representation intentionally separates stable queryable facts from extensible
contract data: relational tables remain useful for parameters, anchors, relations, constraints,
profiles and states, while transform/visual/geometry fields are stored in component metadata JSONB.
No renderer or per-pixel path was connected to PostgreSQL.

### Verification

- targeted A7 + migration + optional PostgreSQL pytest — **12 passed, 1 skipped**
- full `python -m pytest -q` — **PASS**
- `python -m compileall -q src tests` — **PASS**
- live PostgreSQL — **NOT CLAIMED**; no configured DSN/server in this environment
