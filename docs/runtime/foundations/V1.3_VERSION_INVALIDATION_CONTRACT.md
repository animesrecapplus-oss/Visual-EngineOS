# V1.3 — Version / Invalidation Contract

## Problem

A future geometry/render cache must never reuse a result after a relevant upstream change. Clearing the whole cache is correct but unacceptable for a large entity graph; guessing dependencies is faster but unsafe.

V1.3 therefore establishes the identity contract before implementing the geometry cache.

## Version stamp

`VersionStamp` contains three independent boundaries:

- `engine`: implementation version;
- `schema`: serialized model/database schema version;
- `resolution`: semantic resolution-contract version.

A change to resolution semantics invalidates results even if component data is byte-for-byte unchanged.


## Canonical cross-surface version policy

The three default boundaries are owned by `runtime/version_policy.py`:

- `ENGINE_VERSION = "1.3.5"` — executable/package behavior;
- `SCHEMA_VERSION = "2"` — serialized entity schema;
- `RESOLUTION_VERSION = "12"` — resolution semantics and cache identity.

`VersionStamp()` consumes these constants. The package `__version__` and canonical
entity-record serialization consume the same policy, so the previous engine/schema
conflation in `persistence.schema` is no longer possible through the default path.
`pyproject.toml` remains packaging metadata and is checked against `ENGINE_VERSION`
by the A6 verifier.

PostgreSQL migration identifiers such as `008_v1_3_relation_dependencies` remain
separate: they identify ordered schema-changing operations in the migration ledger,
not the semantic serialized-schema version. Forcing those identifiers to equal
`SCHEMA_VERSION` would collapse two different lifecycle concepts.

Explicit `VersionStamp(...)` values remain supported for historical/reproducibility
checks; they do not mutate the current policy.

## Content fingerprint

`component_fingerprint(component)` hashes all local resolution-relevant content:

- identity/kind;
- parameters and anchors;
- relations and constraints;
- profiles;
- appearance and state layers;
- parent linkage;
- transform;
- visual contract and visual overrides;
- geometry contract.

The fingerprint is content-based rather than dependent on Python's randomized `hash()`.

## Dependency fingerprint

A target resolution depends on the target and every ancestor because ancestors can affect:

- world transform;
- z;
- inherited visual values;
- opacity/visibility;
- state context.

Therefore `dependency_fingerprint(target)` hashes the ordered ancestor chain. A sibling change does not invalidate an unrelated target.

## External context

`ResolutionContext` is independently fingerprinted. Changing active states, shadow parameters, or occluder IDs therefore changes the resolution identity without pretending the component itself changed.

## Resolution identity

`ResolutionFingerprint` combines:

`component_id + dependency_digest + context_digest + VersionStamp`.

Its `cache_identity` is a SHA-256 digest over that canonical structure.

This is the key that a future compiled-geometry/render cache can safely use.

## Invalidation rule

For target `A`, a local change to:

- `A`, or
- any ancestor of `A`

invalidates `A`.

A sibling outside that dependency chain does not.

A version-boundary change invalidates all results using the old version stamp, even when content fingerprints are unchanged.

## Important subtlety: mutable Python objects

The engine's `Component` model is currently mutable for construction ergonomics. A manual revision counter alone would be unsafe because callers can mutate nested dictionaries/lists without incrementing it. The dependency contract therefore uses content fingerprints as the correctness mechanism. A future revision counter may become an optimization hint, but it must never replace content validation unless mutation is centrally controlled.

## Cache policy boundary

V1.3 does **not** claim that the geometry cache exists. It establishes the invalidation identity needed to implement one safely. Cache storage, eviction, persistence, memory accounting, and compiled-geometry dependency graphs remain a later layer.
