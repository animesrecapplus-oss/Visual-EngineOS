### Implemented

- Added `runtime/domain_resolution.py`.
- Added `DomainResolutionStatus` with explicit `UNRESOLVED`, `RESOLVED`, `PARTIAL`
  and `REJECTED` lifecycle states.
- Added `DomainDependency` for named, content-addressed upstream dependencies.
- Added `DomainResolvedField` so resolver outputs can only use fields already
  declared by the corresponding `DomainContract`.
- Added `DomainResolutionInput` with single-domain ownership, canonical states,
  explicit resolver identity/version, dependency identities and re-validation of
  every `AppearanceContribution`.
- Added `DomainResolutionResult` with target/domain ownership, input identity,
  resolver identity, status, explicit unresolved reasons, provenance and dependency
  identity.
- Added `DomainResolutionProvenance` and deterministic provenance digest.
- Added `build_domain_resolution_input()` for canonical construction.
- Added `validate_domain_resolution_result()` for fail-closed result validation.
- Added `unresolved_domain_result()` so the current system can explicitly represent
  the absence of a domain algorithm instead of pretending that a domain was resolved.
- Exported the new contract objects from `runtime/__init__.py`.
- Advanced `VersionStamp.resolution` from `9` to `10` because the resolver contract
  changes the resolution identity boundary.
- Added `docs/runtime/appearance/V1.3_DOMAIN_RESOLUTION_CONTRACT.md`.
- Added `tests/unit/test_v13_domain_resolution.py`.

### Semantic safeguards

The new boundary rejects mixed-domain inputs, STATE/EFFECT routing into rendering
resolvers, duplicate dependencies, stale input digests, resolver identity mismatches,
unknown output fields, invalid output values, missing provenance for successful/partial
results, and partial results without explicit unresolved reasons.

The boundary does not normalize, clamp, mix, shade, render or reinterpret domain
values. It also does not create an inheritance mechanism or a second state/effect
policy engine.

## V1.3 — BASE Domain Resolution — 2026-09-15

Implemented the first concrete appearance-domain algorithm after the generic
Domain Resolver Input/Result Contract. The algorithm is intentionally strict: BASE
currently resolves one authoritative opaque `base_color` and refuses to invent
precedence or alpha-compositing semantics that the upstream contracts do not define.

### Implemented

- Added `runtime/base_resolution.py`.
- Added `BASE_RESOLVER_ID` and `BASE_RESOLVER_VERSION`.
- Added `build_base_resolution_input()` as the BASE-specific construction entry point.
- Added `resolve_base_domain()` with explicit cardinality and opacity rules.
- Preserved `#RRGGBBAA` as semantic data without interpreting its alpha.
- Reused the generic `DomainResolutionResult` and validator rather than creating a
  second result protocol.
- Added dedicated BASE regression tests.
- Exported the BASE resolver through `runtime/__init__.py`.
- Advanced `VersionStamp.resolution` from `10` to `11` because the concrete resolver
  algorithm changes resolution identity.
- Added `docs/runtime/appearance/V1.3_BASE_DOMAIN_RESOLUTION.md`.

### Fail-closed safeguards

The resolver rejects zero contributions, multiple BASE contributions without declared
precedence, and translucent contribution opacity without an explicit underlay. It
never selects by declaration order, source-name order, randomness or hidden priority.
The generic domain contract still rejects malformed colors and unknown fields before
the algorithm can consume them.
