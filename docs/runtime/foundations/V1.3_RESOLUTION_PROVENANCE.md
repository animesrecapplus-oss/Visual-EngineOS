# V1.3 — Resolution Provenance Contract

## Goal

A resolved component must be explainable field by field. Debugging cannot depend on reading a final value and guessing where it came from.

## Data model

`ResolutionStep` records:

- `field` — resolved field (`fill_color`, `contour`, `material`, `opacity`, `visibility`, transform, z, shadow, states, etc.);
- `component_id` — component contributing the decision;
- `action` — `set`, `replace`, `inherit`, `override`, `multiply`, `compose`, `accumulate`, `apply`, or `none`;
- `policy` — semantic rule used;
- `detail` — deterministic human-readable explanation.

`ResolutionProvenance` stores immutable ordered steps and exposes `for_field()` and `final_source()`.

The old string `ResolutionTrace` remains for compatibility; provenance is the authoritative structured diagnostic layer.

## Required semantics

- root visual fields are explicit;
- legacy descendant `VisualContract` remains explicit for backward compatibility;
- `VisualOverrides(None)` means inherit, never “default value”;
- opacity and visibility multiply through the hierarchy;
- contour/material overrides are field-level;
- external shadow is an effect, not a mutation of source contracts;
- active state names are merged deterministically;
- world transform and z carry explicit composition policies.

## Determinism

Provenance order follows the ancestor chain and fixed field ordering. The provenance object has a SHA-256 digest suitable for diagnostics and test assertions.

## What provenance does not do

It does not invent semantics for state conflicts, relations, constraints, appearance-layer ordering, or geometric occlusion. Those systems need their own policies before they can truthfully appear as resolved provenance.
