# V1.3 — Generic Component Contract

## Status

**Active hardening milestone.** The generic visual and geometry foundations are implemented and tested. The inheritance/resolution layer is now partially implemented. V1.3 is **not closed**.

## Purpose

V1.3 generalizes the guarantees discovered while building the eye. The eye is one component type, not the architecture itself.

Every renderable component can participate in the same generic model:

```text
Component
├── Identity
├── Parameters
├── Anchors
├── Relations
├── Constraints
├── Profiles
├── State
├── LocalTransform
├── VisualContract
├── VisualOverrides
└── GeometryContract
```

## Generic visual contract

`VisualContract` is a complete explicit local contract:

```text
fill
contour
material
opacity
visibility
```

Defaults are explicit:

```text
fill       = #ffffff
contour    = #000000
material   = default
opacity    = 1
visibility = 1
```

A default value in `VisualContract` is therefore **not** the same thing as inheritance.

## Explicit inheritance

`VisualOverrides` exists to represent child requests against an already resolved parent:

```text
None = inherit
value = explicit override
```

Contour and material have field-level override objects so a child can change one attribute without replacing the whole structure.

Legacy `Component.visual` remains an explicit local contract to preserve compatibility with earlier versions.

## Generic geometry contract

```text
GeometryContract
├── coordinate_frame
├── bounds
├── primitives
├── paths
├── surfaces
├── masks
├── anchors
└── local_z
```

Geometry is authored locally. Parent transforms are resolved by runtime. The geometry contract is renderer-neutral and does not prescribe SVG paths, raster buffers, meshes or GPU formats.

The current path grammar validates:

```text
M = 2 numeric values
L = 2
C = 6
Q = 4
Z = 0
```

Unknown commands and incorrect arity are rejected.

## Runtime resolution

The generic resolver now exposes:

```text
ResolutionContext
        ↓
resolve_component()
        ↓
ResolvedComponent
```

`ResolutionContext` currently carries:

- external shadow;
- occluder IDs;
- active state names.

`ResolvedComponent` carries:

```text
component_id
kind
visual
geometry
trace
```

The `kind` field is descriptive metadata. The resolver must not branch on it to invent semantic rendering rules.
