# V1.37 — COLOR Consumer Audit — Implementation Report

**Date:** 2026-09-25  
**Checkpoint:** V1.37_COLOR_CONSUMER_AUDIT  
**Previous certified checkpoint:** V1.36 corrected COLOR downstream audit

## Executive result

V1.37 re-opened the V1.36 consumer graph, compared the current production runtime against
the immutable V1.36 source fingerprint, and traced the only production consumer that actually
changes a color: `runtime/effects.py` delegates to `runtime/effect_color.py`.

That transformation is already certified as `effect.color.srgb8-interpolation`. It did not
appear after V1.36. The current runtime contains **171 production Python files with zero
added, zero removed and zero changed files** relative to the V1.36 corrected checkpoint.

Therefore the correct implementation of this brick is an **audit-only V1.37 checkpoint**.
No second transformation was invented and no runtime color behavior was modified.

## 1. Baseline and graph re-check

The V1.36 corrected checkpoint was materialized first. Its `artifacts/releases/v1.36/manifest.json`
was used as the baseline for the 171 production Python source files. SHA-256 comparison
returned:

- added: 0
- removed: 0
- changed: 0

This makes the phrase “new path since V1.36” testable instead of inferred from timestamps.

## 2. Actual modifying consumer

The single real downstream color transformation consumer is:

`src/visual_engine/runtime/effects.py`

It calls `_apply_canonical_effect()`, which delegates to:

`src/visual_engine/runtime/effect_color.py::apply_effect_color()`

The owner is therefore `effect_color.py`; `effects.py` is the orchestration/consumer layer.
The operation identifier is `effect.color.srgb8-interpolation`, version `1`.

It is a **true color transformation**, not a representation conversion, measurement, palette
lookup, or renderer operation. However it is **pre-existing** and already closed by V1.34/V1.36.

## 3. Definitive separation

- Representation: `ColorRGBA.to_rgba8()` / `from_rgba8()` at the explicit operation seam.
- Measurement: OKLab distance remains measurement only.
- Palette: palette selection provides canonical colors; it does not mix channels.
- Rendering: renderer RGBA arithmetic remains renderer-owned.
- Transformation: the existing encoded-sRGB8 effect interpolation only.

No new HSL, OKLab or XYZ arithmetic was found downstream. No new generic RGB transform
was found either.

## 4. Contract audit

The existing operation was re-checked across all requested axes: input/output spaces and
representations, alpha semantics, bounds, neutral state, extremes, gamut, provenance,
lineage, dependencies, fingerprinting, invalidation, cache behavior, determinism,
performance and visual criteria.

No contract hole justified a second implementation in V1.37.

## 11. Next step — V1.38

V1.38 should not add another generic COLOR transform automatically. The next micro-scope is
an **effect-color semantic closure audit** around the existing operation:

1. enumerate every caller of `apply_effect_color()` and `_apply_canonical_effect()`;
2. prove that every caller supplies the same alpha/provenance semantics;
3. audit repeated fill/contour application for lineage identity and duplicate work;
4. measure actual render cost for zero, one and multiple color effects;
5. test operation-version invalidation against serialized artifacts and external caches;
6. test adversarial effect ordering and duplicate IDs;
7. render a multi-effect visual board and inspect whether the encoded-sRGB8 law remains
   visually coherent for dark, midtone and high-luminance colors;
8. only if that audit uncovers a *different* real transformation, freeze its contract before
   implementing it.

The key constraint remains: **no new color algorithm without evidence of a distinct real
consumer and a frozen semantic contract.**
