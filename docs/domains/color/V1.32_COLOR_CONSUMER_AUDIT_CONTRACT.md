# V1.32 — COLOR Consumer Audit Contract

**Date:** 2026-09-23  
**Baseline:** V1.31 Typed COLOR Consumer Migration  
**Checkpoint:** `V1.32_COLOR_CONSUMER_AUDIT`

## 1. Purpose

V1.32 is an evidence gate before another COLOR-domain migration. It must answer a
specific question from the production tree:

> Does a real downstream production consumer of the typed COLOR-domain result exist?

The audit must not turn every occurrence of a color-related field into a COLOR
consumer. `base_color`, `palette`, `pattern`, saturation-like parameters,
`ColorRGBA` conversion helpers and effect colors have different ownerships and
must be classified before any migration is attempted.

## 2. True consumer definition

A **true downstream COLOR consumer** is production code outside
`runtime/color_resolution.py` that actually invokes `resolve_color_domain()` or
`resolve_color_domain_from_typed()` and consumes the resulting COLOR-domain
value.

A resolver definition, an export, a test, persistence, a Palette authority, an
EFFECT-domain color operation, or a generic visual-contract color is not enough.

If no true consumer exists, the correct result is `NONE_WARRANTED`; inventing a
migration target is prohibited.

## 3. Required audit surface

The audit records evidence for:

1. `AppearanceDomain.COLOR` references;
2. `base_color`;
3. `pattern`;
4. `palette`;
5. `contrast`;
6. `saturation`;
7. `vibrance`;
8. `lightness`;
9. `temperature`;
10. `resolve_color_domain()` and `resolve_color_domain_from_typed()`;
11. `ColorRGBA`/sRGB conversion entry points;
12. production code that could be mistaken for a downstream COLOR consumer.

AST traversal is used so identifier and attribute references are not reduced to
untrusted substring matches.

## 4. Classification

Every recorded finding receives one category:

- `canonical_color` — typed COLOR authority/projection/resolver infrastructure;
- `legacy_compatibility` — explicit legacy representation or bridge;
- `color_operation` — actual color-space conversion/coordinate operation;
- `palette` — Palette authority or semantic slot selection;
- `effect` — EFFECT-domain color behavior;
- `supporting_infrastructure` — persistence or other supporting boundary;
- `non_color_domain` — reference belongs to another domain.

A finding is never labelled dead merely because a search cannot find a caller.
Dead-code classification requires independent reachability evidence. V1.32 has
zero such proven dead-code candidates.

## 5. Migration rule

If exactly one genuine downstream COLOR consumer exists, it becomes the only
candidate for migration. If zero exist, no migration is performed. If multiple
exist, the audit must enumerate them before selecting any migration target; no
ranking or arbitrary choice is permitted.

## 6. Color-operation rule

If a real consumer performs saturation, contrast, vibrance, lightness,
temperature, mixing, pattern-to-color conversion or another transformation,
implementation is blocked until its contract specifies:

- input color space;
- calculation space;
- output color space;
- channel ranges and boundary behavior;
- alpha representation and whether alpha participates in the operation;
- gamut policy;
- authored/inherited/generated provenance;
- authority and lineage;
- dependency fingerprint;
- invalidation rules;
- deterministic behavior;
- visual acceptance criteria;
- performance/caching implications.

No implicit clipping, gamut mapping, compositing, lighting, shading, material
response or renderer-specific grading is introduced by this audit.

## 7. V1.32 result

The production tree contains 170 Python files and 206 recorded relevant findings.
There are zero downstream production callers of the typed COLOR resolver, zero
unclassified findings and zero proven dead-code claims. Therefore:

```text
MIGRATION_STATUS=NONE_WARRANTED
MIGRATION_TARGET=NONE
```

This is a successful audit result, not a missing implementation.
