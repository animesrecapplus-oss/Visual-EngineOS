# V1.31 — Typed COLOR Consumer Contract

**Date:** 2026-09-23  
**Checkpoint:** `V1.31_TYPED_COLOR_CONSUMER_MIGRATION`

## 1. Purpose

V1.31 promotes the first genuinely typed consumer of the `COLOR` appearance
domain. The goal is deliberately narrow: take the already-selected semantic
`AppearanceRoleContribution`, project only the data that COLOR owns, and return
its canonical linear-sRGB RGBA value without modifying it.

This closes the architectural distinction:

```text
BASE domain
  = legacy-compatible base-color authority / field

COLOR domain
  = typed color-domain consumer of the selected semantic role
```

The two domains may originate from the same upstream role, but they are not the
same resolver and COLOR does not call the BASE resolver or reconstruct its legacy
hexadecimal representation.

## 2. Canonical path

```text
AppearanceComposition
        ↓
AppearanceRoleContribution
        ↓
TypedAppearanceInput
        ↓
TypedColorInput          ← V1.31 minimal COLOR projection
        ↓
DomainResolutionInput(COLOR, role_contribution=...)
        ↓
COLOR resolver
        ↓
canonical ColorRGBA + typed provenance
```

`TypedColorInput` intentionally retains only:

- target ID;
- selected `AppearanceRoleContribution`;
- a fingerprint derived from those two values and the COLOR input version.

It does **not** copy contour, material, opacity, visibility, active states,
appearance layers, geometry, transforms or renderer state into COLOR identity.

## 3. COLOR vocabulary

The V1.31 typed output vocabulary is:

| Field | Value space | Meaning |
|---|---|---|
| `color` | canonical `ColorRGBA` | linear-sRGB RGB + unassociated alpha |
| `role` | `primary/secondary/accent/detail/background/custom` | semantic color role |
| `source` | `base/palette` | selected upstream authority family |
| `authored_srgb` | optional `#RRGGBB` / `#RRGGBBAA` | exact authored representation when one exists |

The generic COLOR contract retains its historical compatibility fields (`base_color`,
`pattern`, `palette`, `contrast`, `saturation`, `vibrance`, `lightness`,
`temperature`) so older callers are not silently broken. V1.31 does not interpret
those fields. They are not an alternate typed COLOR authority.

## 4. Canonical value space

The resolved `color` is the existing V1.24 `ColorRGBA` representation:

- RGB is linear sRGB in `[0,1]`;
- alpha is unassociated in `[0,1]`;
- no premultiplication;
- no implicit clipping;
- no gamut mapping;
- no transfer-function round trip during resolution.

The resolver returns the exact `ColorRGBA` object carried by the role contribution.
This avoids an unnecessary linear → sRGB → linear quantization path.

## 5. Provenance and lineage

The result carries:

- role fingerprint;
- authority component ID;
- source ID;
- authority lineage;
- explicit `appearance_role_bridge` dependency identity;
- resolver ID/version;
- complete domain input/dependency digests.

The resolver does not reconstruct provenance from the color value. It forwards the
already validated upstream provenance.

## 6. Dependency and invalidation rules

The COLOR dependency set is limited to the selected semantic role and explicitly
supplied domain dependencies.

A COLOR identity must remain unchanged when only these change:

- target geometry;
- target transform;
- contour;
- material;
- opacity/visibility metadata;
- renderer state;
- unrelated sibling components.

Authority changes that can alter the selected BASE/Palette role invalidate COLOR.
The existing role-bridge invalidation logic remains the authority for this decision,
and V1.31 prefixes the reason with `COLOR depends on selected role:` rather than
inventing a second invalidation algorithm.

## 7. Fail-closed rules

V1.31 rejects rather than guesses when:

- the resolver receives another domain;
- no typed role is supplied;
- a typed role is combined with a second legacy COLOR contribution;
- MATERIAL or LIGHTING data is supplied to the COLOR domain envelope;
- the typed COLOR fingerprint is tampered with;
- the role dependency fingerprint contradicts the selected role;
- the selected role itself is invalid under the existing role-bridge contract.

There is no implicit legacy COLOR fallback in this checkpoint.
