## 7. Performance measurement and self-critique

The benchmark uses `time.perf_counter_ns()` against the real `resolve_effects()` path,
with 300 warm-up calls and 5 × 4000 measured calls per case.

Final local diagnostic measurement:

| Color effects | Median ns/call | Ratio vs 0 |
|---:|---:|---:|
| 0 | 677-ish | 1.00× |
| 1 | ~95,000 | ~140× |
| 2 | ~183,000 | ~270× |
| 4 | ~376,000 | ~550× |
| 8 | ~749,000 | ~1100× |

Exact machine measurements are retained in
`artifacts/v138_effect_color_closure/V1.38_EFFECT_COLOR_PERFORMANCE.json`.

The cost is approximately linear with the number of color effects after the first effect.
The 0-effect path remains lazy and does not instantiate canonical colors.

A V1.37-vs-V1.38 diagnostic comparison was also performed. The stronger lineage and
invalidation contract adds measurable overhead, while V1.38 removes redundant effect-color
fingerprinting and redundant base RGBA8 decoding. The measured difference varies with local
CPU/process noise; it is **not** presented as a production performance certification.

The important engineering conclusion is that the new correctness requirements were not
hidden behind a cache or renderer shortcut. The cost is visible, bounded and recorded.

## 8. Visual QA

Generated from actual `resolve_effects()` output:

`artifacts/v138_effect_color_closure/V1.38_MULTI_EFFECT_RUNTIME_BOARD.png`

The board covers:

- very dark colors;
- mid tones;
- highlights;
- close colors;
- complementary colors;
- partial alpha;
- zero effects;
- one shadow;
- two shadows;
- shadow→tint;
- tint→shadow;
- four effects.

The visual inspection showed continuous, plausible transitions without an unexpected second
color operation. Alpha-bearing rows retain their alpha in the emitted RGBA values and remain
visibly distinct over the checker underlay.

The complementary and multi-effect cases visibly demonstrate that effect ordering is not a
cosmetic metadata distinction: changing the order produces a different actual color result.
