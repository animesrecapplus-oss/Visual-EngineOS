# V1.29 — Typed Appearance Input Promotion — Implementation Report

Date: 2026-09-23  
Checkpoint: `V1.29_TYPED_APPEARANCE_INPUT_PROMOTION`

## 1. Objective

V1.29 closes the authority gap left deliberately open by V1.28. V1.28 proved that a selected
BASE/Palette role could cross into the legacy `AppearanceResolutionInput.base_color` boundary
without losing provenance. V1.29 makes the typed role itself the canonical renderer-neutral input
for BASE-domain resolution, while retaining the hexadecimal field only as a derived compatibility
representation.

The brick was implemented as a narrow contract promotion. No lighting, shading, BRDF, material
physics, transmission compositing, reflection, style response or gamut mapping was added.

## 3. Architecture implemented

```text
BASE / Palette authority
        |
        v
V1.27 composition
        |
        v
V1.28 AppearanceRoleContribution
        |
        v
V1.29 TypedAppearanceInput
        |
        v
DomainResolutionInput(role_contribution=...)
        |
        v
BASE domain resolver
        |
        v
DomainResolutionResult + role provenance
```

`TypedAppearanceInput` contains the selected typed role plus the renderer-neutral contour,
material, opacity/visibility, active-state, appearance-layer and non-BASE contribution context.
It deliberately contains no geometry, transform or renderer-state fields.

## 4. Canonical typed envelope

New file:

`src/visual_engine/runtime/typed_appearance_input.py`

The envelope enforces:

- one target;
- one `AppearanceRoleContribution`;
- matching target IDs;
- no second BASE authority;
- canonical active-state ordering;
- unique contribution IDs;
- deterministic content fingerprint;
- derived `legacy_base_color` property only;
- conversion back to the legacy input through an explicit compatibility method.

The fingerprint includes the role contribution fingerprint and the rest of the renderer-neutral
semantic input. Geometry and transforms are absent by construction.

## 5. BASE domain promotion

`DomainResolutionInput` now has an optional typed role. The role is legal only for
`AppearanceDomain.BASE`; it cannot coexist with a legacy BASE contribution.

`build_domain_resolution_input()` automatically adds a dependency named
`appearance_role_bridge` whose digest is exactly the role contribution fingerprint. A caller that
supplies the same dependency name with a different digest is rejected rather than silently
replaced.

`build_base_resolution_input_from_role()` is the explicit canonical factory.

`resolve_base_domain()` now follows this order:

1. validate BASE domain ownership;
2. if a typed role exists, read only its derived compatibility representation after the role's own
   invariants have passed;
3. propagate typed role identity into provenance;
4. resolve and validate the BASE domain field;
5. retain the old contribution path only for pre-V1.29 compatibility.

The canonical typed path therefore does not create a second BASE authority.

## 6. Provenance propagation

`DomainResolutionProvenance` now records:

- `role_bridge_fingerprint`;
- `role_authority_component_id`;
- `role_source_id`;
- `role_lineage`.

The result validator compares these values against the input role. A result cannot claim role
provenance when the input had no typed role.

The canonical role is represented in the domain provenance contribution identity as
`role:<role-fingerprint>`. This was added deliberately rather than pretending that a legacy
`AppearanceContribution.contribution_id` existed for the typed role.

## 7. Self-critique and corrections

Two concrete issues were caught during implementation rather than hidden:

### Correction A — provenance validator mismatch

The first typed BASE implementation emitted a role-specific contribution identity while the
existing generic validator still expected only legacy contribution IDs. The validator was updated
to distinguish the canonical typed role identity. The final result is fail-closed and provenance is
not fabricated.

### Correction B — persistence test scope

The first persistence test assumed child components were serialized with a parent component payload.
Inspection of the actual serialization contract showed that the payload persists the component
authority, not an arbitrary child graph. The test was corrected to restore the persisted authority
and then attach a fresh generic target. This tests the real persistence boundary instead of a
fictional round-trip.
