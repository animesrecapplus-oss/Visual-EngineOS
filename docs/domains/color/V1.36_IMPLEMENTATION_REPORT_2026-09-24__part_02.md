## 7a. Release reproducibility correction

A post-packaging independent replay exposed a real release-evidence defect: the first V1.36
verifier depended on a temporary `/mnt/data/v135_work/...` baseline ZIP that is not part of a
clean release environment. The production runtime itself was byte-identical to V1.35, but the
released evidence could not reproduce that claim without the temporary path.

The correction is intentionally evidence-only:

- the trusted V1.35 ZIP was re-read during packaging; all 171 production Python file SHA-256
  values were captured in `artifacts/history/v1.36/color_downstream/V1.35_RUNTIME_BASELINE_SHA256.json`;
- the verifier now consumes this immutable packaged fingerprint rather than a machine-specific
  path;
- the V1.35 generated artifact directory remains removed; no obsolete V1.35 visual artifact
  was restored;
- the pre-existing V1.35 effect regression test was rewritten to assert the still-closed effect
  contract directly from the V1.36 audit/runtime, so the clean checkpoint no longer references
  deleted V1.35 artifacts.

This correction does not alter `src/visual_engine`; it makes the V1.36 evidence self-contained.

## 8. Visual evidence and self-critique

The runtime board uses actual resolver outputs for BASE and Palette, actual renderer Canvas
output for alpha compositing, and an actual eye SVG/raster output. The board was visually
inspected before release.

During implementation, the visual QA script initially referenced a non-existent `geometry.point`
module. This was corrected to the repository's actual `visual_engine.math.Vec2` type before the
visual gate was accepted. A second self-check also removed duplicate renderer-file enumeration
from the audit. These were implementation defects caught before certification, not hidden
failures.

No mathematical-only artifact is used as proof of visual behavior where a real runtime sample
was available.

## 14. Final conclusion

V1.36 found no new generic COLOR transformation that can be implemented honestly without
inventing a feature. The correct engineering result is therefore **no runtime modification**.
The canonical COLOR boundary remains small and explicit, the eye domain remains isolated,
renderer-local RGBA behavior remains renderer-owned, and the next operation must originate from
a proven real production transformation rather than from a desired feature list.
