# V1.31 Implementation Report — Typed COLOR Consumer Migration

**Date:** 2026-09-23  
**Checkpoint:** `V1.31_TYPED_COLOR_CONSUMER_MIGRATION`  
**Baseline:** `V1.30_TYPED_BASE_CONSUMER_MIGRATION`

## 1. Objective

Implement the next architectural brick after V1.30: the first genuinely typed
consumer of the `COLOR` domain.

The requirement was deliberately narrow:

```text
selected semantic role
        ↓
minimal typed COLOR projection
        ↓
COLOR domain
        ↓
canonical ColorRGBA + provenance
```

The implementation must not turn COLOR into a synonym for BASE and must not
introduce lighting, shading, material response, grading or arbitrary color
operations merely to make the artifact look richer.

## 2. What was actually implemented

### 2.1 `TypedColorInput`

New file:

`src/visual_engine/runtime/color_resolution.py` — **226 lines**

`TypedColorInput` contains only:

- `target_id`;
- `AppearanceRoleContribution`;
- a deterministic fingerprint over those values and the COLOR input version.

It intentionally excludes:

- geometry;
- transform;
- contour;
- material;
- opacity/visibility;
- active state payload;
- appearance layers;
- renderer state;
- unrelated siblings.

This is an important dependency boundary: `TypedAppearanceInput` itself contains
more information than COLOR owns, so the COLOR projection must not simply reuse
its whole fingerprint.

### 2.2 Generic domain contract extension

`src/visual_engine/runtime/appearance_contract.py`

The existing generic COLOR vocabulary remains backward-compatible, but the closed
validator now also knows the typed COLOR output fields:

- `color` → canonical `ColorRGBA`;
- `role` → explicit semantic role vocabulary;
- `source` → `base` or `palette`;
- `authored_srgb` → optional authored hexadecimal representation.

A new `canonical_color` value kind validates the actual `ColorRGBA` type. It does
not perform conversion or normalization.

### 2.3 BASE != COLOR

`src/visual_engine/runtime/domain_resolution.py`

A validated `AppearanceRoleContribution` is now permitted as an authoritative
role hand-off for **BASE or COLOR**. This is not a merger of domains:

- BASE still owns its compatibility `base_color` representation;
- COLOR consumes the selected semantic role as a COLOR-domain value;
- a second contribution in the same domain is rejected.

The generic boundary still rejects role contributions for unrelated rendering
domains.

### 2.4 Direct typed hand-off

`src/visual_engine/runtime/typed_appearance_input.py`

Added:

```python
TypedAppearanceInput.to_color_domain_input()
```

The method projects only the role into `TypedColorInput`; it does not copy the
entire appearance envelope into COLOR identity.

### 2.5 COLOR resolver

The resolver identity is:

```text
COLOR_RESOLVER_ID      = color.authoritative-role
COLOR_RESOLVER_VERSION = 1
```

`resolve_color_domain()` is deliberately an identity-preserving resolver.
For a valid typed role it returns the **same canonical `ColorRGBA` value** carried
by the role contribution. There is no linear→sRGB→linear round trip.

Resolved fields are emitted in deterministic order:

- `authored_srgb` when authored provenance exists;
- `color`;
- `role`;
- `source`.

Generated colors do not acquire a fabricated authored representation.

### 2.6 Provenance

The COLOR result preserves:

- role fingerprint;
- authority component ID;
- source ID;
- source lineage;
- explicit `appearance_role_bridge` dependency;
- resolver identity;
- input digest;
- dependency digest.

No provenance is reconstructed from a hexadecimal color string.

### 2.7 Invalidation

`color_domain_invalidation()` delegates to the existing role-bridge authority
invalidation rules.

This prevents a second, potentially divergent invalidation algorithm from being
invented. It also preserves the existing composition-mode semantics: an unused
BASE or Palette authority does not become a false COLOR dependency.
