## 5. Performance decisions

The migration was intentionally optimized instead of blindly converting every
color on every resolution:

1. components with only opacity/visibility/occlusion effects perform no color
   conversion;
2. fill and contour colors are materialized lazily only when a shadow/tint
   actually occurs;
3. each effect color is decoded once per effect and reused for fill and contour;
4. no global palette conversion or renderer-wide color pass was introduced;
5. the existing component resolution cache/invalidation mechanism remains the
   sole cache identity.

## 6. Compatibility decision

`apply_shadow_color(base: str, effect)` remains available only as an explicit
legacy adapter. Static audit evidence confirms there are zero internal production
calls to this adapter after migration.

This prevents two independent color implementations from silently diverging.

## 7. Self-critique and corrections

### Correction A — accidental alpha expectation

The first focused test expected the wrong encoded value for
`#12345680 + 25% white`. Runtime produced `#4d678080`; the test was corrected
against the actual established sRGB8 arithmetic before certification.

### Correction B — legacy alpha loss

The old helper stripped base alpha. The migration made alpha preservation explicit
and added a dedicated alpha-bearing runtime sample. This is a semantic correction,
not a visual embellishment.

### Correction C — unnecessary conversion cost

The first migrated implementation eagerly decoded base fill/contour even when
only scalar effects were present. It was revised to lazy materialization so
non-color effects retain the previous lightweight path.

### Correction D — effect color alpha ambiguity

The existing contract already exposed `VisualEffect.alpha` as effect strength.
The effect color's optional alpha byte was therefore not promoted to a second
opacity authority. Tests explicitly prove that changing only the effect-color
alpha does not change the RGB effect result.
