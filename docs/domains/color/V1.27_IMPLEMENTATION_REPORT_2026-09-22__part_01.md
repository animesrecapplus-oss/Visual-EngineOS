# V1.27 Implementation Report — Effective Appearance Composition Foundations

Date: 2026-09-22
Checkpoint: `V1.27_EFFECTIVE_APPEARANCE_COMPOSITION`
Baseline: V1.25 certified source checkpoint; V1.26 palette contract reconstructed from the preserved V1.26 implementation report because the V1.26 source ZIP was not mounted in the active filesystem.

## Executive result

V1.27 establishes a renderer-neutral appearance composition boundary between typed BASE (V1.25)
and typed Palette (V1.26). Composition is **selection, not color mixing**.

The result keeps BASE and Palette as separate authorities and records their fingerprints/provenance.
The resolver never invents a third color authority, never averages colors and never composites alpha.

## Implemented contract

### 1. Typed Palette authority

A `Palette` contains typed `PaletteEntry` values for `primary`, `secondary`, `accent` and `detail`.
Entries are stored as a tuple so duplicate slots can be detected rather than silently overwritten by
a dictionary.

### 2. Source identity

Palette source is explicitly `authored`, `inherited` or `generated`.
Generated palettes require generator ID/version and cannot claim authored representations.

### 3. Provenance

The palette stores target component, authority component, source ID, ordered lineage, rule and optional
generator identity. Inherited palettes retain the original authority and lineage.

### 4. Inheritance and override

The nearest palette authority is resolved as one whole authority. Supported policies are:

- `LOCAL_WINS`
- `INHERIT_WINS`
- `REJECT_CONFLICT`

A blocking nearest authority cannot be bypassed by a more distant ancestor. A missing slot remains
missing; slots are never mixed between authorities.

### 5. Canonical color

Every palette entry is canonical linear-sRGB RGBA. Authored sRGB spelling is preserved exactly.
There is no gamut mapping, clipping, alpha compositing or color interpolation.

### 6. Targeted invalidation

Palette fingerprints contain only palette authorities relevant to the target. Geometry, transforms,
materials, lighting and unrelated siblings are absent. Local `LOCAL_WINS` palette authority is not
invalidated merely because an ancestor palette changes.

### 7. Typed composition

`AppearanceCompositionRequest` supports explicit modes:

- `BASE_ONLY`
- `PALETTE_ONLY`
- `BASE_THEN_PALETTE`
- `PALETTE_THEN_BASE`
- `REJECT_SAME_ROLE`

`BASE_THEN_PALETTE` is the default: a BASE value with the requested semantic role wins; if no matching
BASE role exists, the matching Palette slot may supply the value.

No hidden fallback exists. `background` and `custom` BASE roles do not implicitly map to `primary`.

### 8. Provenance preservation

The composition result retains:

- BASE fingerprint/authority when present;
- Palette fingerprint/authority when present;
- selected source;
- selected Palette slot.

### 9. Composition fingerprint

The fingerprint contains only composition version, target, explicit request, BASE resolution identity,
Palette resolution identity and selected slot. Geometry and transforms cannot alter it.

### 10. Persistence

Palette metadata is serialized and reconstructed with fingerprint verification. Tampered fingerprints
fail closed. No PostgreSQL migration was invented for this renderer-neutral metadata boundary.

## Adversarial coverage

The focused suite covers:

- duplicate semantic slots;
- generated palette without generator provenance;
- authored source/canonical contradiction;
- missing slot without fallback;
- nearest-authority isolation;
- blocking inheritance;
- `INHERIT_WINS`;
- `REJECT_CONFLICT`;
- local-wins invalidation narrowing;
- sibling non-invalidation;
- geometry independence;
- typed-vs-legacy palette authority conflict;
- contradictory composition requests;
- role mapping failures;
- explicit requirements;
- BASE-only / Palette-only isolation;
- same-role conflict rejection;
- BASE and Palette mutation changing composition identity;
- persistence round-trip;
- persistence tampering.

## Generic/non-ocular evidence

The same contract is exercised with a generic `object` and a non-ocular `hand` component. No eye module
is imported by the palette/composition implementation.

The ocular branch remains a Golden-Component stress test rather than an owner of the appearance model.
