# V1.35 — VisualEffect COLOR Surface Audit — Implementation Report

**Checkpoint:** V1.35 VisualEffect COLOR Surface Audit  
**Date:** 2026-09-24  
**Baseline:** V1.34 First Real Downstream COLOR Operation  
**Runtime semantic version:** `1.3.8`  
**Resolution semantic version:** `18`  
**Schema version:** `2`

## 1. Executive result

V1.35 was implemented as the next brick defined by V1.34: audit the remaining real
`VisualEffect` color surface before introducing another color algorithm.

The audit found exactly one distinct RGB color operation in the generic effect surface:

```text
shadow ─┐
        ├── effect.color.srgb8-interpolation (v1)
tint ───┘
```

The other three production effect kinds are scalar operations:

```text
opacity    → scalar opacity
visibility → scalar visibility
occlusion  → scalar visibility + opacity
```

No second COLOR transformation was found. No saturation, contrast, vibrance,
lightness, temperature, mixing, pattern-to-color, grading, lighting, shading,
material or gamut operation was invented.

One genuine cleanup was warranted: `runtime/contract.py::_apply_shadow` contained a
second, direct encoded-RGB implementation but had zero repository call sites. It was
removed only after a repository-wide call-site proof. The canonical `effect_color.py`
operation remains the sole RGB transformation boundary.

## 2. Why this is a real brick

V1.34 migrated the first existing color operation. The danger at V1.35 was to interpret
the remaining effect vocabulary as evidence for additional color algorithms. That would
create false architecture and duplicate semantics.

The V1.35 audit therefore asks four separate questions:

1. What are all production `VisualEffect` kinds?
2. Which kinds actually change RGB?
3. Through which production paths are effects created or injected?
4. Does any direct RGB arithmetic remain outside the explicit canonical boundary?

Only after these questions were answered was cleanup performed.

## 3. Production surface audited

The audit parsed **171 production Python files**.

### Effect kinds

| Kind | Actual behavior | COLOR operation |
|---|---|---|
| `shadow` | RGB transform | `effect.color.srgb8-interpolation` |
| `tint` | RGB transform | `effect.color.srgb8-interpolation` |
| `opacity` | scalar opacity | none |
| `visibility` | scalar visibility | none |
| `occlusion` | scalar visibility + opacity | none |

The result is intentionally not five color algorithms.

## 4. Effect creation paths

The audit traced the actual production construction/injection paths.

### 4.1 Explicit resolution context

`ResolutionContext.effects` accepts already validated `VisualEffect` objects.
`ResolutionContext.effective_effects()` additionally injects the legacy shadow compatibility
effect when `shadow_alpha` is non-zero.

### 4.2 Legacy shadow compatibility

`runtime/contract.py` still owns the legacy input fields:

```text
shadow_alpha
shadow_color
```

They are converted to one ordinary `VisualEffect(kind="shadow")` with explicit metadata:

```text
origin=legacy_shadow
```

This is compatibility input, not a second RGB algorithm.

### 4.3 Relation-generated effects

`runtime/dependencies.py::relation_effects()` accepts an explicit
`relation.metadata["effect"]` mapping and constructs `VisualEffect(**payload)`.
The target defaults and `effect_target` rules remain unchanged.

The `kind` value is dynamic at this boundary, but it is immediately validated by the
canonical `VisualEffect` constructor. This is a validated passthrough, not unresolved
dynamic dispatch. The audit therefore records it explicitly instead of falsely calling
it a static literal or falsely treating it as unsafe.

### 4.4 Consequence-generated effects

`runtime/consequence_bindings.py` converts an accepted `EffectConsequenceBinding`
into `VisualEffect`. The binding constructor itself validates its effect kind by creating
a canonical validation instance.

Again, this is an existing validated dynamic value, not a hidden fifth or sixth effect kind.

## 5. Shadow and tint semantic equivalence

The production `resolve_effects()` branch is:

```text
if effect.kind in {"shadow", "tint"}:
    decode base/effect ColorRGBA
    apply_effect_color(...)
```

There is no separate shadow algorithm and no separate tint algorithm.

Both use:

```text
operation_id      = effect.color.srgb8-interpolation
operation_version = 1
calculation_space = srgb-encoded-8bit
```

This was deliberately preserved from V1.34. V1.35 does not change the artistic law.
