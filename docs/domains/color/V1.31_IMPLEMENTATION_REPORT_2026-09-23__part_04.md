### Step 3 — if the consumer changes the color, define the operation first

For any real operation such as saturation, contrast, temperature, vibrance,
pattern or mixing, define before implementation:

- input value space;
- output value space;
- operation domain (sRGB, linear-sRGB, HSL, OKLab, etc.);
- alpha semantics;
- authority and precedence;
- provenance/lineage;
- dependency fingerprint;
- invalidation scope;
- out-of-gamut policy;
- behavior at degenerate/edge inputs;
- deterministic serialization;
- visual acceptance criteria.

### Step 4 — visual validation

The next artifact must compare the actual runtime operation against a known
reference or a deliberately constructed semantic test where the expected visual
effect is unambiguous. A numerically correct artifact that looks visually wrong
must fail review.

### Step 5 — preserve the boundary

Do not introduce lighting, shading, BRDF, material physics, transmission,
reflection or renderer-specific post-processing merely because a color operation
would look more impressive with them. Those remain separate future domains.
