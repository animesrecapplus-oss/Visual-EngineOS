# V1.30 — Typed BASE Consumer Migration — Implementation Report

**Date:** 2026-09-23  
**Checkpoint:** `V1.30_TYPED_BASE_CONSUMER_MIGRATION`

## 1. Objective

V1.30 was executed as the next micro-brick after V1.29. The objective was not
to add another appearance algorithm, but to prove that the canonical typed
appearance input is actually consumed by internal BASE-domain code rather than
merely existing beside the legacy API.

The acceptance target was:

```text
typed role → typed appearance input → BASE domain
```

with the historical hexadecimal appearance input retained only where an explicit
compatibility boundary requires it.

## 2. Starting point

The working tree was created by extracting the certified V1.29 checkpoint
`visual_engine_v1.29_typed_appearance_input_PROMOTION_CERTIFIED_checkpoint.zip`.
The V1.29 report and contract were inspected before modification.

No V1.28/V1.29 superseded visual-artifact directories were carried into the final
checkpoint as current evidence.

## 3. Consumer audit before modification

A source search showed that the legacy `build_appearance_input()` call remained
only in:

- `runtime/appearance_contract.py` — its definition;
- `runtime/appearance_role_bridge.py` — the typed role compatibility bridge;
- `runtime/typed_appearance_input.py` — the explicit legacy escape hatch.

The BASE resolver already accepted typed role data from V1.29, but there was no
single typed-envelope convenience seam proving that internal callers should use
the typed object itself. V1.30 closes that ambiguity.

## 4. Implementation

### 4.1 Typed BASE hand-off

`TypedAppearanceInput.to_base_domain_input()` was added. It delegates to a new
`build_base_resolution_input_from_typed()` function and forwards the existing
`AppearanceRoleContribution` unchanged.

`resolve_base_domain_from_typed()` was added as the direct resolver convenience
entry point.

Neither function reconstructs `AppearanceContribution(base_color=...)`.

### 4.2 Compatibility isolation

`TypedAppearanceInput.as_legacy_appearance_input()` remains available and is now
documented as the explicit compatibility escape hatch. No internal BASE-domain
consumer uses it.

### 4.3 Static migration gate

`tools/verify_v130_legacy_consumer_migration.py` scans `src/` for
`build_appearance_input(` calls and fails if a new call appears outside the three
explicit compatibility boundaries.

This is intentionally narrow: it does not claim that every occurrence of the
word `base_color` is legacy. Typed `BaseColor` is a legitimate canonical model
and is not treated as a violation.

## 5. Self-critique and corrections

### Correction 1 — wrong RuntimeGraph import in the first test draft

The first test draft referenced a non-existent `runtime.runtime_graph` module.
Repository inspection showed the canonical implementation is `runtime.graph`.
The test was corrected rather than adding a duplicate import facade.

### Correction 2 — wrong BaseColorRole member in the first test draft

The test initially assumed a `BASE` enum member. Inspection of the actual model
showed the semantic roles are `PRIMARY`, `SECONDARY`, `ACCENT`, `DETAIL`,
`BACKGROUND` and `CUSTOM`. The test was corrected to use the canonical `PRIMARY`
role rather than inventing a new enum value.

### Correction 3 — authored representation versus canonical resolver output

The compatibility path intentionally preserves authored spelling such as
`#AaBbCc80`, while the BASE domain contract canonicalizes the resolved hexadecimal
value to lowercase. The visual/test comparison therefore compares semantic hex
case-insensitively while separately preserving authored spelling. Treating the
case difference as a semantic mismatch would have been a false positive.

### Correction 4 — tampering test

A test initially attempted to alter an authored legacy string independently of
its role fingerprint. The role contract correctly rejected that object before it
could reach the typed envelope. The test was replaced with a direct fingerprint
tamper case that exercises the actual fail-closed boundary.
