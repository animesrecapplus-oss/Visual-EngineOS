# V1.6 — MOR Canthus Endpoint Tangent Profile

## Status

**IMPLEMENTED — ENGINEERING PASS / VISUAL ACCEPTANCE OPEN**

This brick follows V1.5 and separates the four geometric lid/canthus junctions:

- inner upper;
- inner lower;
- outer upper;
- outer lower.

It does **not** claim that any chosen values reproduce an anatomical truth or a universal anime
style. The two supplied reference sheets remain stylistic evidence. The previous reference
analysis found multiple eye-construction families and explicitly warned against treating the
canthus as a triangular closure. No original Bézier vectors are available in this checkpoint, so
no numeric reference truth band is invented. The clean reference sheet measurements available in
`V1.4_MOR_REFERENCE_MATH_SPEC_PREANALYSIS.md` remain envelope measurements rather than canthus
control-point ground truth.

## Why V1.6 exists

V1.5 exposed two transition controls, one per corner. That was still too coarse: both upper and
lower lid junctions at the same corner were forced through the same tangent policy. The rendered
V1.5 sweep also showed that simply redistributing curvature can create a swollen visual cap.

V1.6 therefore separates **which endpoint tangent changes** from **how much the corner transition
is lengthened**.

## Public authoring contract

`CanthusEndpointTangentProfile` contains:

- `angle_deg ∈ [-45,45]`: local tangent rotation in the canonical eye frame;
- `length_scale ∈ [0.25,2]`: multiplicative tangent-handle scale;
- `influence ∈ [0,1]`: interpolation from the V1.5-resolved baseline to the requested profile.

Four instances are exposed by `EyeParameters`:

- `canthus_inner_upper_profile`;
- `canthus_inner_lower_profile`;
- `canthus_outer_upper_profile`;
- `canthus_outer_lower_profile`.

The default profile is `(0°, 1.0, 0.0)` for all four endpoints. This preserves the V1.5 output
exactly.

## Geometry algorithm

1. V1.5 first resolves a safe baseline tangent handle from local endpoint spacing and corner gap.
2. The endpoint's existing local tangent direction is measured from the adjacent sampled lid.
3. `angle_deg * influence` rotates that direction.
4. `length_scale` is interpolated from `1` toward the authored value using `influence`.
5. The resulting handle is capped at `0.95 ×` the local pre-profile tangent spacing.
6. The endpoint itself is never moved.
7. The first two interior samples are rewritten along the resulting tangent ray.
8. The existing renderer-neutral cubic bridge is rebuilt from the resulting C1 derivatives.
9. Existing continuity and self-intersection checks remain hard gates.

The bridge remains a four-control-point cubic. No renderer-specific approximation is introduced.

## Invariants

1. All profile values are finite.
2. All values remain inside the declared authoring domain.
3. `influence=0` is exact V1.5 compatibility, even if angle/length are non-default.
4. Each endpoint profile changes only its own first/last two sampled lid points.
5. The opposite canthus is unchanged by an isolated endpoint profile.
6. Semantic canthus coordinates do not move.
7. Iris and pupil geometry do not move.
8. The profile is evaluated in the eye's local frame before the existing global rotation.
9. The existing C1 continuity contract remains mandatory.
10. Existing finite-coordinate and self-intersection guards remain mandatory.
11. Zero/covered/closed opening keeps its existing degenerate-opening contract.
12. A profile is not accepted merely because numerical metrics improve.

## Adversarial axes covered

- all nine current eye morphology families;
- opening `1.0`, `.82`, `.35`, `.02`, and exact zero boundary;
- global rotation `-30° … +30°`;
- diagonal gaze after the lid-follow stage;
- isolated modification of each of the four endpoints;
- angle-only and length-only behavior;
- influence interpolation;
- non-finite and out-of-domain authoring;
- semantic anchor invariance;
- internal ocular assembly orthogonality;
- bridge derivative change;
- topology/self-intersection safety.

## Visual QA rule

Clean renders and sampled diagnostics are generated separately. The sampled diagnostic contains 33
points evaluated directly from the exact cubic stored by the engine. It is evidence of sampling,
not a replacement for the clean render.

A visually bad result remains bad even when:

- C1 is exact;
- the curve is simple;
- curvature metrics improve;
- the manifest is deterministic.

### Current visual finding

The V1.6 endpoint profiles demonstrably change the intended tangent data. However, close inspection
of the clean canthus renders still reveals a pre-existing rendering/closure problem: the cubic
closure is stroked with the full contour width and therefore can read as a thick vertical cap at
small corner gaps. Some endpoint-angle variants can also make that cap asymmetrical.

This is **not** silently accepted as a visual improvement. No non-zero V1.6 profile is promoted as a
global default.

## Reference comparison boundary

The checkpoint contains the previous mathematical analysis of the two reference sheets and their
measured contour envelopes, but not the original reference pixel files themselves. Therefore this
brick generates engine-side family sweeps and does not fabricate a pixel-overlay comparison.
Reference digitization is a separate required brick.

## Non-goals

This brick does not:

- digitize reference Bézier curves;
- infer anatomy from stylized drawings;
- solve renderer stroke caps;
- declare a universal anime canthus profile;
- solve the complete upper/lower lid family;
- implement epicanthic-fold semantics;
- promote a visual style preset.
