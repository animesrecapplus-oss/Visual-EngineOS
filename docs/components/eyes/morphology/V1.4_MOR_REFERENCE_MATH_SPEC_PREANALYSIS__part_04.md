# 16. Vecteur morphologique proposé pour formalisation future

Le moteur pourrait travailler avec un vecteur compact de niveau MOR :

```text
W/H_ref
open_ratio
t_open
opening_balance
upper_apex_u
upper_apex_v
upper_curvature_mean
upper_curvature_peak
lower_apex_u
lower_apex_v
lower_curvature_mean
lower_curvature_peak
inner_transition_length
inner_tangent_start
inner_tangent_end
inner_curvature_mean
inner_curvature_concentration
outer_transition_length
outer_tangent_start
outer_tangent_end
outer_curvature_mean
outer_curvature_concentration
upturn_downturn_delta
asymmetry_global
asymmetry_upper
asymmetry_lower
epicanthic_strength
epicanthic_length
epicanthic_lateral_amplitude
epicanthic_curvature
```

Les valeurs absolues ne doivent pas être hardcodées dans une seule fonction ; les unités physiques n'existent pas ici. Tout doit rester dans le repère normalisé de l'œil.

# 17. Axes sous-estimés à ne pas perdre

1. position du maximum d'ouverture ;
2. position du maximum de courbure ;
3. longueur de transition du canthus ;
4. concentration de la courbure ;
5. indépendance upper/lower ;
6. pente locale au canthus ;
7. amplitude latérale du pli médial ;
8. séparation du pli et du contour ;
9. ségrégation canthus/cils ;
10. asymétrie locale vs asymétrie globale ;
11. repère nominal vs repère visible ;
12. containment de l'iris/pupille ;
13. visibilité indépendante de la géométrie ;
14. dégénérescence contrôlée à `opening -> 0`.

# 18. Règle d'or pour la suite

Aucun prompt ou paramètre MOR ne doit être mappé directement sur un mot artistique sans passer par une grandeur mesurable.

Exemples :

```text
« gros iris »
→ iris_diameter / W = valeur

« pupille décalée vers la droite »
→ dx/W > 0
→ d_iris <= containment_limit

« œil très étroit »
→ open_ratio dans une bande mesurée

« canthus doux »
→ Delta_theta + K_bar + C_rho dans une bande validée

« œil très rond »
→ W/H_ref + open_ratio + t_open conjointement
```

La chaîne correcte est donc :

```text
mot utilisateur
    ↓
concept sémantique
    ↓
paramètres normalisés
    ↓
invariants
    ↓
géométrie
    ↓
QA mathématique
    ↓
QA visuelle
```

# 19. Décision pour la prochaine étape

**Ne pas coder immédiatement tout le vecteur ci-dessus.**

La prochaine micro-étape doit être la formalisation de seulement trois familles :

1. `EnvelopeMetrics` ;
2. `CanthusMetrics` ;
3. `EpicanthicMetrics`.

Avant de modifier la géométrie, nous pouvons ainsi produire un rapport numérique sur les références et sur notre moteur actuel : **mêmes métriques, mêmes unités, mêmes définitions**.

C'est ce qui permettra ensuite de comparer objectivement :

`référence → moteur → écart → correction`.
