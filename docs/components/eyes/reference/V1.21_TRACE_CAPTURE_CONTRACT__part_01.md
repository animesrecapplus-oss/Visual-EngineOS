# V1.21 — Source-Pixel Trace Capture / Difficult-Contour Workbench

**Date:** 2026-09-20  
**Status:** ENGINEERING PASS / TRACE CAPTURE READY / HUMAN APPROVAL GATE UNCHANGED

## 1. Why V1.21 exists

V1.20 established the correct fail-closed rule: segmentation cannot silently become
anatomical truth. During implementation review of the actual preserved 792×792
reference, a second limitation became concrete: a source candidate can contain only
one connected dark-ink component even though the reviewer still needs independent
upper and lower traces.

Candidate 014 is the observed example. The source-pixel component inventory reports
exactly one eligible connected component for that candidate. A component-only API
therefore cannot represent independent upper/lower selections without inventing a
split.

V1.21 addresses that implementation blind spot without relaxing the human gate.

## 2. V1.21 contract

The trace pipeline is now:

```text
preserved source bytes
  ↓
V1.20 semantic review
  ↓
V1.21 reviewer-selected trace region
  ↓
component proposal OR explicit manual source-pixel polyline
  ↓
terminal coordinates
  ↓
source ReferenceCurve
```

A manual polyline is not a fitted curve and is not an anatomical inference. It is a
sequence of source-pixel coordinates explicitly captured by the reviewer.

## 3. Trace-region correction

V1.20 documentation promised that a contextual segmentation box could be narrowed to
a smaller eye-specific trace region, but the executable V1.20 record had no separate
field for that region. V1.21 introduces `TraceRegionV121` while retaining the original
V1.20 `source_bbox` as provenance.

This matters because a large face panel may contain multiple independent dark-ink
components. Component IDs must be resolved inside the reviewer-selected trace region,
not against an oversized contextual panel.

## 4. Two explicit trace modes

### Component mode

The reviewer selects a machine-produced component ID.

The machine continues to provide only:

- component bounding box;
- component area;
- orientation-independent centerline proposal.

The component is not called upper/lower by the machine.

### Manual mode

The reviewer draws the upper/lower contour directly over the source pixels.
The stored points remain in source-image coordinates.

Validation requires:

- at least four points;
- finite coordinates;
- no consecutive duplicate points;
- explicit medial/lateral terminals through the V1.20 semantic review;
- explicit trace direction normalization relative to the medial terminal.

No spline, Bézier, polynomial, or hidden smoothing model replaces the captured points.

## 5. Explicit manual-selection identifiers

For an approved review that uses manual upper/lower traces, V1.20 now accepts the
reserved identifiers:

- `__manual_upper_trace__`
- `__manual_lower_trace__`

Both must be present together. A single manual sentinel mixed with a component ID is
rejected. This makes the exceptional path explicit rather than hiding it behind a
fake component ID.

V1.20 component digitization still rejects those sentinels; V1.21 consumes them only
when matching manual source-pixel traces are supplied.

## 6. No automatic semantic split

The component inventory is diagnostic. V1.21 does **not** attempt to split a connected
stroke into upper/lower anatomy using curvature, color, pupil location, or geometric
heuristics.

That class of heuristic could generate visually plausible but semantically false
labels. The human must provide the separation.

## 7. Offline review workbench

`tools/visual_qa_v121_trace_capture.py` creates a self-contained HTML workbench with:

- all 28 candidate IDs;
- actual source pixels embedded in the artifact;
- candidate-specific crop/trace region;
- component-count inventory;
- component/manual mode selection;
- upper/lower/epicanthus trace capture;
- medial/lateral terminal clicks;
- reviewer notes;
- import/export of a V1.21 trace manifest.

The workbench edits only local browser state. It never creates an approval status and
never promotes calibration.
