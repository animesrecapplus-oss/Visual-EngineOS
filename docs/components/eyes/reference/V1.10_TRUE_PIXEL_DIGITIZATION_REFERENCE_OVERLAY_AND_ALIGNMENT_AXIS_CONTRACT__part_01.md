# V1.10 — True Pixel Digitization + Reference/Engine Overlay + Alignment-Axis Rotation

Date: 2026-09-18

## 1. Scope

V1.10 adds two independent but related capabilities:

1. **ocular alignment-axis rotation** as a depth/foreshortening operation distinct from the existing 2D circular roll;
2. **true pixel-reference infrastructure** for source validation, human-reviewed segmentation, dense curve digitization, independent endpoint measurements, and reference-vs-engine overlays.

The uploaded 792×792 JPEG is preserved byte-for-byte as a **user-supplied review sheet**. It is not asserted to be either historical original from V1.9 because its provenance, original canvas and upstream crop history are unknown.

## 2. Axis model

### Existing axis

`EyeParameters.rotation_deg` remains the established **screen/view-axis roll**. It rotates the eye in the image plane and, for a bilateral pair, rotates the interocular centerline around its midpoint.

### New axis

`EyeParameters.alignment_axis_rotation_deg` is the **alignment-axis depth rotation**. The alignment axis is the local X axis: the line along the ocular alignment/interocular direction.

The current renderer is 2D, so this is deliberately a renderer-neutral **2.5D orthographic projection**:

```text
local ocular plane
       |
       | rotate around local X
       v
Y' = Y * cos(alignment_axis_rotation_deg)
X' = X
       |
       | then apply existing screen roll
       v
world/image plane
```

Consequences:

- horizontal extent is preserved by the orthographic projection;
- vertical extent is foreshortened by `|cos(angle)|`;
- iris/pupil/reflection ellipses are decomposed into projected principal radii and orientation;
- lid margins, creases, canthi, caruncle and epicanthic geometry inherit the same ocular transform because their source points are projected before world placement;
- brow geometry uses the same local-frame scale before its existing parent roll;
- the two axes can be combined without one being silently interpreted as the other.

This is **not** claimed to be a full 3D eyeball, eyelid-surface, or perspective head model. Perspective-dependent side-view behaviour remains a separate future layer.

## 3. Bilateral and multi-eye inheritance

For a default human pair:

- the new alignment-axis angle is shared through the same `EyeParameters` unless explicitly overridden;
- small left/right differences are allowed only within `EyePairPolicy.max_alignment_axis_rotation_delta_deg`;
- alignment-axis rotation does **not** move the eye centers in the current orthographic model;
- existing roll still rotates the pair centerline around the pair midpoint;
- every ocular child receives the projected transform through geometry ownership rather than renderer-specific guesses.

For a multi-eye creature, each `EyeParameters` can carry its own alignment-axis angle, while a parent component can expose an inherited semantic angle through `LocalTransform.alignment_axis_rotation_deg` and `resolve_alignment_axis_rotation()`.

## 4. Parent transform contract

`LocalTransform.alignment_axis_rotation_deg` is semantic 2.5D metadata. It is intentionally **not** inserted into the generic 2D affine matrix: doing that would incorrectly turn a depth rotation into a screen roll.

`resolve_alignment_axis_rotation()` accumulates the value along the root→target hierarchy. The ocular façade exposes it through `OcularTransformResolution.alignment_axis_rotation_deg`.

This keeps the generic runtime honest while giving the ocular domain an explicit inherited depth-orientation channel.

## 5. Prompt-facing vocabulary

Stable semantic names are provided in `gaze/semantics.py` so later prompt parsing can refer to ocular intent without embedding renderer commands.

Canonical examples:

```text
look_forward
look_left
look_right
look_up
look_down
look_behind_right_eye
look_behind_left_eye
look_behind_both_eyes
```

The important case is:

```text
"look behind with right eye"
        -> look_behind_right_eye
        -> eye = right
        -> yaw_deg = 180
        -> requires_depth_projection = true
```

The current 2D GazeSolver must **not** silently turn this into `screen-right` or `screen-left`. The semantic intent therefore records the required depth operation and remains explicitly non-renderable by the present 2D gaze solver. A future 3D ocular/gaze backend can consume the same stable name.

## 6. V1.10.1 source validation

Implemented:

- SHA-256;
- dimensions;
- detected format;
- EXIF orientation state;
- expected-format/expected-orientation checks when supplied;
- temporary download + fail-closed verification from V1.9;
- byte-preserving local storage with digest-guarded no-overwrite;
- explicit crop status.

A standalone uploaded image cannot prove that no crop/rescale happened before upload. Therefore `crop_status = unknown` unless provenance supplies an authoritative canvas expectation.

## 7. V1.10.2 human-assisted segmentation

`segment_reference_sheet()` produces candidate foreground boxes without assuming a fixed grid.

The workflow is mandatory:

```text
candidate
   ↓
preview
   ↓
human validation
   ↓
TraceRegion(approved=True)
   ↓
explicit component selection
   ↓
ReferenceSample
```

No candidate is automatically promoted.

The current uploaded sheet produced 28 foreground candidates. The review artifact intentionally shows these boxes and keeps every candidate `pending_human_review`.
