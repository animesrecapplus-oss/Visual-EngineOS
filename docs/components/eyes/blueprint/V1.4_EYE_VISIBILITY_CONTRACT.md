# V1.4 — Eye granular visibility contract

## Purpose

Every named ocular granularity has an explicit boolean visibility state. Visibility
is a presentation/authoring concern and is intentionally excluded from geometry
identity and geometry-cache inputs.

## Hierarchy

The canonical tree is owned by `components/face/eyes/visibility.py`. Examples:

- `pupil -> pupil_glow, pupil_smoke`;
- `iris -> limbal_ring, crypts, fibres, radial_structure, pigmentation, rings, microstructure`;
- `highlight -> reflection, reflection_marks`;
- `canthi -> inner_canthus, outer_canthus, epicanthic_fold`;
- `sclera -> sclera_spots`.

An explicit `false` parent disables every descendant. Siblings remain independent.
Therefore `without pupils + with highlight` disables the pupil subtree while leaving
highlights available. An explicit child cannot resurrect itself through a disabled
ancestor; this prevents contradictory inherited state.

## Prompt semantics

The visibility contract is ready for the future prompt compiler, but the current
parser/semantic IR is still partial. No claim is made that free-form prompts already
compile automatically into this tree. Once `PRM.parser` and `PRM.semantic_ir` are
implemented, a general phrase such as “without pupils” should resolve to the `pupil=false`
node, not to unrelated siblings. More specific clauses should modify only the named
granularity.

## Defaults versus user intent

Project defaults are aesthetic coherence defaults and hard validity invariants are
geometry safety rules. They are not a ban on authoring. Explicit user parameters are
allowed to override aesthetic defaults. Hard invariants remain enforced because a
request that produces NaN, invalid topology or an impossible contract cannot be
rendered safely.

This distinction is mandatory: **default aesthetic policy is not the same thing as
authoritative user intent, and neither is the same thing as a geometric validity invariant.**
