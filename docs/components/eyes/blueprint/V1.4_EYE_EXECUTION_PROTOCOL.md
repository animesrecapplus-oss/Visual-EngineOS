# V1.4 — Eye execution protocol

## Mandatory lifecycle

Before implementing an atom, perform a **structural ownership check**: identify the narrowest existing module that owns the responsibility. If that module mixes unrelated responsibilities or exceeds the eye implementation budget, refactor it first. Never append a new domain to a compatibility facade or a mixed-responsibility file merely because it is convenient.

Every atom follows exactly this evidence loop:

`DEVELOP → TEST → ARTIFACT → VISUALIZE → CORRECT → VALIDATE → ACCEPT`

### DEVELOP
Define input contract, output contract, parameter domain, ownership, dependencies, invariants and failure behaviour before implementation.

### TEST
At minimum test nominal values, lower/upper bounds, degenerate inputs, composition with neighbouring systems, determinism and cache/provenance impact where applicable. Property-style tests are preferred when a continuous parameter domain exists.

### ARTIFACT
Generate deterministic SVG and, when raster tooling is available, PNG evidence. Store a JSON manifest containing task ID, parameters, seed, engine/schema/resolution versions, input fingerprint and output hashes.

### VISUALIZE
Inspect normal, extreme and interaction cases. A passing numerical test is not a substitute for visual inspection.

### CORRECT
Every visual defect becomes either a parameter/invariant correction, a contract correction, or a documented intentional style choice. Renderer-specific hacks are not accepted as silent fixes.

### VALIDATE
Re-run the atom tests plus affected regression suites. Confirm unrelated atoms did not change unexpectedly.

### ACCEPT
Update the blueprint status, implementation log, decision record when architectural policy changed, and evidence manifest.

## Evidence minimum by class

| Class | Required evidence |
|---|---|
| Geometry | SVG + geometry metrics + boundary cases |
| Appearance | SVG/PNG + colour/appearance manifest |
| Expression | before/after pair + intermediate parameters |
| Camera | same intrinsic eye across shot/camera cases |
| Prompt | prompt + IR + parameters + rendered artefact |
| Variation | deterministic seed matrix + uniqueness/validity report |
| Interaction/Occlusion | source/target/depth/coverage report + visual artefact |
| Infrastructure | unit/property tests + contract/import/cache evidence |

## Anti-false-positive rules

1. Parent completion never implies child completion.
2. A label/preset without measurable geometry/appearance effect is not implemented.
3. A renderer-only effect is not considered a semantic contract.
4. A visual artefact without reproducible inputs is not regression evidence.
5. A test that only exercises nominal values cannot close a boundary-sensitive atom.
6. A deterministic hash does not prove visual equivalence.
7. A camera transform does not prove perspective/3D.
8. A colour field does not prove colour intelligence.
9. An expression preset does not prove a general expression solver.
10. A prompt string stored in metadata does not prove prompt-to-parameter compilation.

## Structural decomposition gate

1. One responsibility has one canonical implementation owner.
2. Parent/child/grandchild concepts are separated when their contracts, tests or change cadence differ.
3. Compatibility facades may preserve historical imports but contain no substantive implementation.
4. Focused eye implementation modules target **≤250 lines**; crossing the budget triggers decomposition review before feature growth.
5. Shared primitives belong in the narrowest genuinely shared contract layer; do not create “common” dumping grounds.
6. A refactor is accepted only after import compatibility, deterministic evidence and the full affected regression suite pass.
