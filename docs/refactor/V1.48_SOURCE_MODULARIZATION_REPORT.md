# V1.48 — Source-code modularization audit and extraction

## 1. Starting point

The V1.47 certified source tree contains 174 Python modules. The audit found 67 modules above 150 lines.
This is an inventory signal, not permission to split 67 files at arbitrary line boundaries.

The direct import graph contains 408 internal edges in V1.47. Three pre-existing strongly connected
components are present in the runtime graph. V1.48 was required to leave those SCCs unchanged; the new
region module does not participate in any of them. The refactor therefore adds no new import cycle.

## 2. Duplicate audit

No exact duplicate function-body groups were found by AST-normalized hashing.

A token-normalized similarity scan found one 97.9% candidate between
`base_resolution.build_base_resolution_input()` and
`material_resolution.build_material_resolution_input()`.
Manual inspection rejected it as a false duplicate: both delegate to the same generic factory, but they
bind different `AppearanceDomain` values, resolver identities and contract versions. Those differences
are part of their domain contracts and must not be merged merely to reduce text repetition.

## 3. Selected module

`src/visual_engine/runtime/visibility.py` was selected because it was 461 lines and had a clear
responsibility seam. Its planar conversion helpers were independently consumed by `region_maps`,
`placement`, `placement_constraints`, attribution and the visibility kernel.

The extracted responsibility is exactly: **materialize renderer-neutral geometry as planar regions and
convert planar results back to the immutable region contract**.

## 7. Performance

Five fresh-process comparison runs were made against the V1.47 source baseline.
Median-of-run medians:

- region conversion: baseline 59,950 ns; V1.48 60,631 ns (+1.14%);
- warm production render: baseline 16,395,562.5 ns; V1.48 15,603,239.5 ns (-4.83%).

The small conversion delta is within normal process/runtime noise; the full production render did not
regress in the measured sample. No optimization unrelated to the extraction was introduced.

## 8. Visual evidence decision

architecture graph was generated and inspected to validate the dependency direction, then deleted. The
real production SVG from the V1.47 baseline and V1.48 refactor is byte-identical: 15,168 bytes and
SHA-256 `7bce6ee07c056452b3c3544beb794c3011a9dc56d9a15c01d21ca75ba4b11696`. No rendered visual

## 10. Artifact retention — later clarification

V1.48 actually removed the entire generated-evidence tree. That was an over-interpretation of the
retention rule. The corrected policy, adopted for V1.49, keeps `artifacts/` and retains only the latest
brick's evidence under `artifacts/current/vX.Y/`; superseded generated contents are purged. The V1.48
checkpoint itself remains outside the project tree as the certified ZIP.

## 11. Next micro-scope

V1.49 should audit the next largest runtime module only after reviewing the current dependency graph.
The next candidate must be chosen from a real responsibility seam, not from file length alone.
The likely candidates are `contract.py`, `appearance_contract.py`, `domain_resolution.py`,
`generators.py` or `placement.py`; no one is selected in advance.

For V1.49 the required sequence is: dependency audit → responsibility map → consumer trace → one seam →
one extraction → focused tests → full regression → benchmark → visual validation only if rendering can
change → documentation → cleanup → checkpoint.
